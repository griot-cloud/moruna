# Decisions

The open questions the architecture document puts to its owner (`architecture/moruna-runtime-design.md`, section 12), with their status, followed by decisions taken during the build that are not one of those questions (ids `S1` and up, for supply chain and similar; the build board's delegated decisions log carries the smaller ones). The PM agent keeps this file current: when a question is decided, the status becomes `decided <date>: <one line>`, the date column is set, and the document or SDD that carries the decision is cited. An escalation item in the preamble (`architecture/sdd/00-preamble.md`, section 7) that traces to one of these questions takes its assumption until the row here says otherwise. Every decision is one line here and as many as it needs in the document it changes; this file is an index, not the argument.

| CM1 | How Moruna knows what a kind costs | Brackly | decided 2026-10-27: measured, not guessed. | KD1 | The format of the settings schema each kind declares (waves brief, MB3 and MC1: FlatBuffers or JSON Schema, one for both MC1 and MC2) | the MC1 executor, as the brief directs (MB3: "pick one"); Brackly may overturn | decided 2026-10-28: JSON Schema 2020-12, derived (`schemars`) from the type each adapter reads its settings with, so the published schema and the check cannot drift. Why: a kind's settings hold values a FlatBuffers schema can only type as opaque bytes (a standard kernel's `args`, which its name decides; a package's `args`; a peQL caller; a filter value that is a number, string or boolean; a `url` that is one string or several), and an open registry cannot be a FlatBuffers union, which is a closed enum that adding a kind would change; JSON Schema describes the open values, the constraints (`enum`, `required`, closed objects) and the examples a screen is drawn from, with validators in every language an embedder writes in. FB1 still holds: in the job spec v2 (MC2) a node is a kind name and its settings, carried in the FlatBuffers spec as a value of the same data model (FlexBuffers) and checked against this schema; JSON is its rendering (SDD 18 e.2). Generating FlatBuffers code would also need `flatc`, which this repository does not have | 2026-10-28 |
