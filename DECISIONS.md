# Decisions

The open questions the architecture document puts to its owner (`architecture/moruna-runtime-design.md`, section 12), with their status, followed by decisions taken during the build that are not one of those questions (ids `S1` and up, for supply chain and similar; the build board's delegated decisions log carries the smaller ones). The PM agent keeps this file current: when a question is decided, the status becomes `decided <date>: <one line>`, the date column is set, and the document or SDD that carries the decision is cited. An escalation item in the preamble (`architecture/sdd/00-preamble.md`, section 7) that traces to one of these questions takes its assumption until the row here says otherwise. Every decision is one line here and as many as it needs in the document it changes; this file is an index, not the argument.

| KD1 | The format of the settings schema each kind declares (waves brief, MB3 and MC1: FlatBuffers or JSON Schema, one for both MC1 and MC2) | the MC1 executor, as the brief directs (MB3: "pick one"); Brackly may overturn | decided 2026-10-28: JSON Schema 2020-12, derived (`schemars`) from the type each adapter reads its settings with, so the published schema and the check cannot drift. Why: a kind's settings hold values a FlatBuffers schema can only type as opaque bytes (a standard kernel's `args`, which its name decides; a package's `args`; a peQL caller; a filter value that is a number, string or boolean; a `url` that is one string or several), and an open registry cannot be a FlatBuffers union, which is a closed enum that adding a kind would change; JSON Schema describes the open values, the constraints (`enum`, `required`, closed objects) and the examples a screen is drawn from, with validators in every language an embedder writes in. FB1 still holds: in the job spec v2 (MC2) a node is a kind name and its settings, carried in the FlatBuffers spec as a value of the same data model (FlexBuffers) and checked against this schema; JSON is its rendering (SDD 18 e.2). Generating FlatBuffers code would also need `flatc`, which this repository does not have | 2026-10-28 |
| MK1 | What the Moruna microkernel (BOARD EK, KB1) is built on, and under which licence | Brackly | decided 2026-10-28: Asterinas's OSTD 0.19.0 (the `ostd` crate) as the hardware layer, holding all the kernel's unsafe code (boot, page tables, interrupts, timers, the frame allocator, task switching, user mode entry), with the microkernel written on it in safe Rust (`#![forbid(unsafe_code)]`); Asterinas's Linux kernel is not used. OSTD and the crates published with it are MPL-2.0, which is accepted because it is file-level copyleft: the MPL files stay MPL with their source available and nothing else in Moruna is touched; it is on the allow list of the kernel workspace's own `kernel/deny.toml` only, so the root workspace's policy is unchanged (SDD 20 a, `kernel/deny.toml`) | 2026-10-28 |
| EN1 | How Moruna's engine runs on its kernel (BOARD EK, KD2): as a Linux program through the personality, or as a native process | KD2 agent (the brief left it to the SDD) | decided 2026-10-29: as a Linux program. The root workspace's engine (`moruna-engine`, the command line of MH 4.2 without the Python adapter), built static for musl and unmodified, runs under the Linux personality, which starts it with `run_granted` (`moruna.linux` 1.2): its process is granted the handles the boot manifest names (`process_grant`, ABI 2.2: the vsock driver, the personality's listener), on a start page its auxiliary vector carries, and it reaches the kernel's own calls on them with the `syscall` instruction, as a task makes `batch_get`. One engine serves both Linux nodes and the kernel; a native engine would be `no_std`, which is a second engine, or a port of Rust's standard library to the kernel's calls, which is a fork to maintain. The data plane's calls, slots and waits are native calls from the Linux program too, so batches cost the same; the forwarded round trip is paid on the engine's file and thread calls only. The personality gained what a tokio program needs: eventfd, epoll, rename, a machine's memory (SDD 30 f.1) | 2026-10-29 |
| EN2 | How a boot's machine gets its vsock where the host has no `/dev/vhost-vsock` (a Mac's VM; coordinator, 2026-10-29: "KD2-T9 must run on this Mac") | KD2 agent | decided 2026-10-29: QEMU's `vhost-user-vsock-pci`, its back end `moruna-vhost-vsock`, a host program of the root workspace (`crates/moruna-vmm/src/vhost_user/`) that runs moruna-vmm's own `VirtioVsock` and muxer over vhost-user messages instead of MMIO. Not rust-vmm's `vhost-device-vsock`: its crates are not in the build's cache and would be fetched, and its host side is the same Firecracker-style Unix-socket protocol the muxer already speaks, so ours is one device, tested once, for both moruna-vmm's VMs and QEMU's. Its version is the workspace's lockfile. The flags are `machine` lines of the boot description; the guest's memory is a shared memfd (SDD 30 f.11) | 2026-10-29 |
| EN3 | How an image's identity is checked on the kernel (coordinator, 2026-10-29: "an image's identity is checked on the kernel") | KD2 agent | decided 2026-10-29: the launcher that attaches an image's layers writes its record (manifest and config byte for byte, each layer's digest and seal); the engine is granted it, asks the personality which layers its programs start on (`moruna.linux` 1.3 `layers`, from `moruna.imagefs` 1.2), and before a task is made checks the entry's digest against the manifest, the config and layers against the manifest, and the layers served against the record, seal for seal, refusing the document (exit 2) naming both sides. A layer's id is its seal (the hash of its header page, which carries the root every page is checked against), so the image filesystem checks the list's id at mount (SDD 27 IF-O5 done). The verified config gives the command and environment through `moruna_image::Launch`, the same rules the sandbox follows. The conversion of an OCI layer into a layer file stays the launcher's to vouch for (SDD 30 f.12, m.4) | 2026-10-29 |
| DP1 | Where the data plane's record check runs (BOARD EK, KD1): in the kernel's `batch_put`, or in a verifier the engine supplies | KD1 agent (the brief left it to the SDD) | decided 2026-10-29: in the engine's process (`moruna-plane`), on a record whose window `batch_put` has already unmapped from the task, before anything else of the engine is told of it. The bytes checked are then the bytes every consumer maps; the kernel keeps no Arrow format and no parser of untrusted flatbuffers (SDD 20 a); the kernel copies no byte of the record, where a check in the kernel must copy the framing out of the frames to read it; and `batch_put` returns as soon as the window is unmapped, so the check is off the task's path. The check is the one IPC check, made `no_std` (`moruna-ipc-check`) and shared with `moruna-kernel` (SDD 29 f.3) | 2026-10-29 |
| VJ1 | How `moruna-vmm` jails each run before it starts QEMU and the vsock back end, so that code escaping the VM holds nothing of the node or of another run (Griot design `local-to-cloud-compute` 4.8, Brackly 2026-11-04) | vmm-jail agent, on Brackly's design | decided 2026-11-04: each process is made by `clone3` into new user, mount, PID, network, IPC, UTS and cgroup namespaces (and into the run's cgroup leaf when the host delegates one, `--cgroup DIR`; `--cgroup none` says it does not, and a named directory that does not delegate `cpu`, `memory` and `pids` is refused), with a tmpfs root holding only its program, the libraries its own loader lists, QEMU's firmware directories as `qemu -L help` lists them, the run's snapshots and disks and the sockets it uses, read-only except its disk, its serial log and its socket directories; `no_new_privs`, locked securebits, every capability dropped, `user.max_user_namespaces` 0, an empty environment; QEMU runs with `-sandbox on,obsolete=deny,elevateprivileges=deny,spawn=deny,resourcecontrol=deny` and the back end installs its own allow-list filter; the run's directory and leaf are removed when the run ends. Identity: a service with `NoNewPrivileges` and no `newuidmap` can map only its own uid, so jailed processes keep the service's uid and groups on the host (`JAIL_ID` 1000 inside); runs are kept apart by the namespaces and filters, not by uid. The descriptor's `user_network` stays, and inside the jail's empty network namespace it reaches nothing off the node (`crates/moruna-vmm/src/jail/`) | 2026-11-04 |
