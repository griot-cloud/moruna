# Changelog

## 0.6.4

What moving the first project onto 0.6.3 found; each fix has a test that fails on 0.6.3.

- **Stateful tasks on separate branches run at once.** Every stateful instance's home worker was its index within its stage, so every single-instance stage (every `moruna.Function` subclass) lived on worker 0 and stages on separate branches ran one at a time. The run's instances are dealt to the workers in turn, across stages.
- **Sources read when polled, not when issued.** The Python, iterator, stream, Parquet and Vortex sources did each read when the drive issued it, and the drive issues up to its read-ahead before it polls, so nothing downstream ran until the source had been read through. The first batch is now processed while later ones are still being read.
- **A run lets go of its arena when it ends.** A `moruna.Function` subclass's kernel kept the arena of the first run it was in, and a reference cycle kept the task and its kernel for good: every run's arena, gigabytes each, stayed mapped until a run was refused for the memory the process held. The arena and the memory gate are bound to a kernel for one run and released when it ends, and a task is freed with its job.
- **A source with nothing to read is a run with no rows.** A fresh run whose plan has nothing to read was refused ("nothing to probe with"), and so was a stage after a join in such a run; both are seeded from their hints, the stateful tasks' `finish` runs and what it gives reaches the sink (SDD 11 f.14 amended).
- **Run arguments take `datetime` and `date`.** They are written as RFC 3339 and `YYYY-MM-DD` (they were written as `str()` and refused); an object JSON cannot write is refused by name. Every task reads an argument as its JSON value, in process as inside an image.
- **A CLI report round-trips through Python at decimal ties.** The canonical writer uses the same shortest-decimal rounding as Python, so `RunReport.from_bytes` does not reject a report just because Rust's float formatter chose another final digit.
- **Schema declarations name structs.** `struct<name: type, ...>`, nested in lists and structs, in `takes` and `gives`.
- **Linux wheels install in task images.** The Linux wheels are built for `manylinux_2_28` (they were `manylinux_2_39`, newer than the images a task is built into) and for aarch64 as well as x86_64 (`tools/release/linux-wheels.sh`).
- **Python images start in the sandbox.** Every Python image `moruna build` made died at its start: with no home, CPython looked the user up, glibc asked nscd over a Unix socket, and the image filter killed the process for it. Images now run with `HOME=/tmp` and `PYTHONNOUSERSITE=1`, which the build key names, so no image built before is reused.
- **A job whose sink is its own task runs its images.** With no `cache` setting an image was unpacked beside a file output, so such a job was refused at every image. Images unpack into Moruna's cache (`$XDG_CACHE_HOME/moruna/unpacked`, else `~/.cache/moruna/unpacked`) when the output is not a local directory.
- **`moruna.run` runs a built job's images.** `moruna.run(..., sandbox_cgroup=, sandbox_python=)` gives the run its sandbox, as `moruna run --sandbox-cgroup` does.
- **A source image can call its ports while it plans.** The run's ports are bound before any source or sink is built.
- **An image the filter kills is named.** A source or sink whose process died was reported only by its broken stream; how it ended now leads the message, with its standard error.
- **A sink image reads what the stage before it gave.** The stream a sink image reads takes the first batch's schema, as the Parquet and Vortex sinks do (an image function plans its input's schema and may give another); a later batch with other columns is refused naming both.
- **An image reads every batch it is given.** A batch whose last buffer had no bytes (a string column of nulls) was written to an image with the zeros after its body, which a stream reader takes for the end of the stream: the image stopped after its first batch.

## 0.6.3

- **A job spec is one self-contained, language-neutral document.** The `python` kind is gone from every role: a task of your own code (a `moruna.Source`, `moruna.Function` or `moruna.Sink` subclass, or a `@moruna.function`) is an `image` task, `{image: {build_key, digest, location}, entry, params, needs}`, and every task carries its **definition** inline, the kind `Declaration` extended with `title`, `description`, `takes` and `gives` (Arrow schemas), `requires` (each need with its description) and `provenance` (build key, source repository, revision, dirty). A custom task makes its definition from its code: its docstring's first line is its title and summary and the rest its description, its constructor's annotated params the JSON Schema of its params, and its `takes`, `gives` and `needs` (a list, or a mapping of name to description). A built-in kind's task carries the kind's declaration, and `check` refuses one that differs, params that do not fit an image task's schema, needs its definition does not require, and an edge whose declared schemas differ. The job carries its declared run arguments. In-process runs (`moruna.run(job)` with Python objects) build nothing and run as in 0.6.2, macOS included. `moruna.Function.build`, `moruna build MODULE:FUNCTION`, `moruna run --resolver` constructing code by reference, the `fingerprint` of a task and the `python` kinds' adapters are gone.
- **Build keys, known before anything is built.** `sha256:` over each file of the task's import closure (its syntax tree with docstrings removed, so a docstring, comment or formatting edit keeps the key and needs no rebuild), its data files' bytes, the lock, the runtime image, the shim, the platform and the entry. `job.spec()` stays instant and complete. Before `job.build()` a spec is a **draft**: complete for drawing and checking, refused for running, naming every unbuilt task. `job.build()` fills each image's digest and location, and that spec's digest names exactly the images that run. The status is read from the spec (`job.status()`, `print(job)`, `job.explain()["images"]`): `not built`, `built`, `pushed` or `external`.
- **`job.build(out, registry=, platform=, ports=, files=)` and `moruna build JOB.mjob` (or `MODULE:ATTRIBUTE`)** build one OCI image per task: the runtime's layers, one layer per Python distribution the task's code imports (the closure's imports mapped to distributions through installed metadata, plus what they require as the lock installed them), the shim, and the task's own code. The closure is found statically inside the project root; an import computed at run time is refused by name, and data files are named by a task's `files` or `--file`. The same content is the same blob, stored once, so tasks share layers; an image already built for a key is reused. `registry=` pushes every image (credentials through the resolver as the need `registry:<HOST>`, never in the spec). Manifests carry `org.opencontainers.image.source` and `.revision` (from git, with `org.moruna.source.dirty`), and `org.moruna.entry`, `.build.key`, `.lock.digest` and `.files` (every bundled file with its sha256). The images stay ordinary OCI images: the shim is the entrypoint, Arrow IPC on standard input and output.
- **Image tasks for every role.** The `image` kind is a source (one Arrow IPC stream on its standard output), a function and a sink (one stream on its standard input, its commit written back as one JSON object) on a Linux node (`moruna-sandbox`, `moruna_sources::ArrowStreamSource`, `moruna_sinks::ArrowStreamSink`); a function's image may give one batch after its input ends (its `finish`). On the Moruna kernel a function's image is checked by its digest and the build key its manifest carries. An image Moruna did not build is a task too: `moruna.image("HOST/REPOSITORY@sha256:...", role=..., entry=...)`, status `external`.
- **Pull by digest.** A registry location is pulled through the OCI distribution API before the run starts, anonymously or with a token or a username and password the resolver supplies, every digest checked, and kept in `~/.cache/moruna/images` by digest. A local layout keeps working.
- **Params, arguments and needs inside an image.** The process gets `MORUNA_ENTRY`, `MORUNA_ROLE`, `MORUNA_PARAMS` and `MORUNA_ARGS` (JSON objects) and, with needs, `MORUNA_PORTS` and `MORUNA_PORT_SOCKET`. A need of an image task is a port the runner serves, over the port protocol (`"MRP1"`, a name, a body; a status and an answer; Arrow IPC for batches; `moruna_sandbox::ports`); inside an image `self.ports[name]` is its client. In process, the resolver keeps handing over objects. The contract is documented in `docs/images.md`.
- **Run arguments.** `job.arg(name, type)` declares an argument (`string`, `int`, `float`, `bool`, `date`, `timestamp`); the spec holds the declaration, never a value. `moruna.run(job, args={...})` and `moruna run JOB --arg NAME=VALUE` supply them, tasks read `self.args`, a missing, ill-typed or undeclared argument is refused by name before the run, and the report records them.
- **The run report is task-level (schema 2.0).** `schema_version` (`MAJOR.MINOR`; a reader refuses an unknown major) replaces `moruna_report`, and `stages` is gone: each task, keyed by its name in the spec, has its status, start and end, wall and busy time, CPU in core-seconds, peak memory, instances, rows, bytes and morsels in and out, throughput, amplification, state, allocations, failures, the time it waited on input and to hand on output, per need the calls, bytes and time (measured through the resolver's object in process and at the port for an image), the plan's prediction beside what was observed, its observation in the cost model's form and a recommendation for memory, CPU and instances with its basis as data. The report also names the Moruna, the host and the run's arguments, and each plan step's actual start and end. Every number names its unit (bytes, milliseconds, core-seconds); a measurement not made is absent, never zero. `resources.cpu_core_s` replaces `cpu_ns`.
- **`moruna run`'s report file is the run report.** The file is schema 2.0 in its canonical bytes, the document `moruna.run` returns and a writer port writes (`moruna.RunReport.from_bytes(path)` reads it); the host protocol's `report` message carries the same document, beside `plan`, how the run went against its plan. The trace-shaped envelope (`moruna_report`, `spec_digest`, `host_notes`, the trace's `report`) is gone: its digest is `job_digest`, its host notes are in `notes`. A run refused before it started has a document too, `exit.status` `"refused"`, every task `skipped`. One builder makes the document for every surface (`moruna_runtime::report_doc`). Rust's canonical JSON (`moruna_job::canonical_json`) writes a float as Python's `json` does (`2.52e-05`, `1500.0`, `1e+16`), so the file's bytes are the bytes `moruna.RunReport.bytes()` writes of the same document; a document's JSON digest changes where it holds a float written differently before.
- **Each task's observation carries its full cost key.** `role`, `kind`, `fingerprint` (an image task's build key; a built-in function's kernel fingerprint; a built-in source's or sink's kind declaration's digest), `settings` and `schema`, with the `run` that measured it, so observations of one task from different runs aggregate; the live learner keys a stage the same way. A store's records name their run (`moruna_cost::Observation::run`, `History::runs`), and with an observation store configured (`moruna run --cost-store`, `moruna.run(cost=...)`) a function's `cpu` and `morsel_duration_ms` recommendations draw on every run of its key the store holds, their basis saying `source` `"store"`, how many runs and how many observations; otherwise the basis is `"this_run"`. A unit's memory is not measured, so an observation's outcome no longer carries the task's peak as a unit's.

## 0.6.2

0.6.1 was never released; its work is part of this release.

- **A run is a `moruna.Job`.** `job = moruna.Job(name)`; `job.add(task, inputs=..., name=None)` adds a task fed by tasks of the job (or their names) and returns it; `print(job)` shows one line per task (its key, role, kind or code reference, params, inputs, needs and schemas). A task's output may feed many tasks and a function may take several inputs; branches ready at the same time run at the same time: four branches that each block for 1 s on one batch take about 1 s, not 4 s. Unknown names, cycles and outputs no task reads are refused with one `ConfigError` naming every one, before anything starts. `moruna.run(job)` runs it, and `moruna.run(source, functions, sink)` is the job of one path. `moruna.Graph`, `moruna.GraphTask` and `moruna.run(graph=...)` are gone (SDD 22 JB-I18, SDD 12 PY-I15).
- **"Function" replaces "kernel" on every public surface.** `@moruna.function` replaces `@moruna.kernel`; `moruna.FunctionError` replaces `moruna.KernelError`; the job document's role 1 is `Function` (its value is unchanged); `moruna kinds` and `moruna.kinds()` list `functions` (listing format 2); `moruna check --function NAME` and `moruna.check(function=...)` report `functions`, each naming its `function`. `moruna.Task` is the base of `moruna.Source`, `moruna.Function` and `moruna.Sink`; a decorated callable, a `moruna.std` function, a loaded package and a task of a `@moruna.kind` are each a `moruna.Function`. `moruna.KernelSpec`, `moruna.StdKernel`, `moruna.PackageKernel` and the module-level `moruna.build` are gone: `function.build(...)` packages a function.
- **A job's spec is its document.** `job.spec()` returns, at any step, the job document version 2 (FlatBuffers, `MJB2`), which now carries the job's `name`: `spec.bytes()`, `spec.digest()` (`sha256:` over exactly those bytes) and `spec.to_json()` (for people). `moruna.Job.read(source)` reads a spec, or any document, back, and writing the job read gives the same bytes. `job.write(target)` and `moruna.run(job, spec_to=target)` go through a writer port: a file path, a callable taking bytes, or any `moruna.Writer` (`write_spec`, `write_report`); an object-store URL is refused. `spec()` refuses, naming the task, an `IteratorSource`, code defined inside a function, a param that is not data and a param that names a secret.
- **Tasks a user writes follow a contract.** A `Source`, `Function` or `Sink` subclass declares `takes` and `gives` (Arrow schemas), `needs` (names the runner supplies, never read by Moruna) and data-only constructor params. A spec names it as a `python` task, `{"ref": "module:Class", "params": {...}, "needs": [...], "fingerprint": ...}`, the fingerprint the one `moruna check` computes, taken of the class; a runner constructs it again from its reference and refuses a fingerprint that differs. The `python` kind of every role takes these settings, in a document and from `moruna run`, and the decorator hints it took before are gone. Declared schemas are checked by `job.check()` and on every batch at run time. A `Function` subclass defines `__call__(self, batch)` and optionally `finish(self)`.
- **Needs are supplied through a resolver port.** `moruna.run(job, ports={name: object})` resolves every need through `moruna.Ports`, the in-process adapter; a host passes its own `moruna.Resolver`, or names it with `moruna run JOB --resolver module:attribute` (and `moruna serve`). A need the resolver cannot supply is refused by name before the run starts; the task reads what it was given as `self.ports[name]`.
- **No secret in a document.** The `object_store` of a job document holds endpoints and names only; its credential fields are deprecated in the schema and never read, and a version 1 document that sets one is refused. `moruna.run(..., storage=...)` supplies credentials to the run, never to its spec, and a host's environment supplies them to `moruna run`.
- **`explain` and `check` live on the job.** `job.explain(planner=None)` plans a job without running it, a job of in-process objects or one read from a spec alike, with the function `moruna explain JOB` uses; `job.check()` checks it. The module-level `moruna.explain` is gone: a document is explained as `moruna.Job.read(path).explain()`.
- **The run report names the job, and has one canonical form.** `moruna.RunReport` carries `job_digest` (the spec's digest), `exit` (`code`, `status`, `diagnostic`), `tasks` (per task: rows and bytes in and out, time, rows set aside), `resources` (CPU time, peak memory), `sinks` (per sink: its task, its target, what it wrote, and the `snapshot_id` and `version` it committed) and, with `explain=True`, `plan`, beside the trace's fields. `report.bytes()` is canonical JSON (sorted keys, no whitespace), `report.digest()` is `sha256:` over exactly those bytes, and `moruna.RunReport.from_bytes(data)` reads them back unchanged; `spec_to` writes the report's bytes after the run. A sink reports what it committed: peQL's snapshot for a `peql` sink, and a `moruna.Sink`'s `finish()` may return `{"snapshot_id": ..., "version": ...}`; a commit without a snapshot is refused. The `limits` alias of `limits_initial` is gone.
- **A version 2 job with a fan-out and a join resumes after preemption**, each of its sinks holding every row once, as an uninterrupted run's do (`moruna-runtime/tests/job_resume.rs`).
- **`moruna.std.join()`, a join of branches of one upstream.** A function of several inputs that, for each morsel, puts the columns every branch gives for it side by side, in input order, keeping the morsel's number. Its inputs must be branches of one source or task through functions of one input, which the build checks; a row count that differs between branches or a column two branches give is refused naming the ports. A fan-out and a join give the same rows as the chain of the same functions. `moruna.std.union()` is now reachable from Python too (SDD 22 JB-I19, SDD 10 SC-I18, SC-T40, contracts CT-T32).
- **A stateful function's `finish` is called, and what it returns goes downstream.** `finish(self, state)` on a stateful Python function's object is called once per instance when the function's input has ended, after its last `__call__`; a batch it returns flows to the next task like any other, `None` gives nothing, and an exception ends the run with a `FunctionError` naming `<function>.finish`. A function that must see the whole run (one that collects every batch and gives one result) does it here with `instances=1`; with more, each instance's `finish` runs. `Kernel::finish` now returns `Option<Payload>` and runs per stage, when that stage's input ends, before its outputs close; its batches are numbered after every number the stage's input carries. No manifest is written after a `finish` has given a batch, and a `resume="reinit"` function resumed from an earlier one sees only what came after it, so a whole-run function that must survive a resume uses `resume="checkpoint"` (SDD 10 SC-I17, SC-T39, SDD 12 PY-I16, PY-T47, contracts CT-T33).
- **moruna-vmm jails every run.** QEMU and `moruna-vhost-vsock` each start in their own jail: new user, mount, PID, network, IPC, UTS and cgroup namespaces, a tmpfs root holding only what the process needs, no capabilities, `no_new_privs`, a seccomp filter refusing new namespaces, and an empty environment; QEMU runs sandboxed, and the back end installs its own allow-list filter before it binds. `boot --cgroup DIR|none` puts each run in a delegated cgroup v2 leaf with memory, CPU and PID limits; the run's directory and leaf are removed when it ends.

## 0.6.0

- Integrates the native node artifact, explicit account and storage grants, and the owned host launch/session interface.
- Adds the native KD3 conformance fixtures and focused regressions for shared build contexts, memory admission, event records, and durable storage.
- Terminates a failed ordered pipeline without waiting forever for queued sink writes whose earlier sequence failed, while retaining submitted I/O until completion.
- Reads iterator sources through actual end of iteration instead of reporting completion after their first batch; an empty batch remains data and later iterator errors remain failures.
- Accepts `None` as empty warm-up options in the check harness and exposes existing report `buffers`, `policy`, and `memory_basis` values through the Python facade.
- Corrects native IPC final-buffer padding, read-only ELF backing reuse, Linux forwarding fairness and readlink error semantics; retains strict memory and admission accounting.
- Validated local ARM Linux and x86 QEMU TCG execution, 15 SDK cases, the public Python builder, the strict scoped 92-result comparison, and a freshly installed free-threaded Python wheel. Kernel TLS, io_uring expansion and UEFI remain outside Phase A.

## 0.5.9

- **`moruna build`: a Python kernel as an OCI image (KA3).** `moruna build <module>:<function>` and `moruna.build(fn)` write an OCI layout the `image` kind runs: the official `python:3.14-slim` layers by digest, the project's locked dependencies installed for `linux/aarch64` or `linux/x86_64` (a `uv.lock` or a `requirements.lock` with hashes; a project with no lock is refused, and nothing is resolved), the Moruna shim, and the function. Layers 2 to 4 are reproducible tars that carry the bytecode of every source (hash based, written by a CPython that matches the runtime's, so nothing is compiled at a start), so the same function is one image bit for bit and two functions of one lock share every layer but the last. The shim reads and writes the Arrow IPC stream of SDD 19 f.6 and needs only `pyarrow`; a module's `import moruna` finds a stand-in of `kernel` and `polars` in the image. `examples/image_job.rs` writes the version 2 job that runs one (SDD 30, BD-T1 to BD-T32).
- **An `arrow_ipc` source (KA9).** Reads the Arrow IPC file format: one file, or a directory of `*.arrow` files in name order. One split per record-batch block (or blocks grouped to `options.split_rows`), with rows and null counts exact from each block's message header and no body read at plan time; a projection with `options.columns`. Every message passes the IPC check before arrow decodes it, and a bad block is a `Source` error naming the file and the block, never a panic. A stream-format file is refused, saying the file format is needed. In Python, `moruna.ArrowIpcSource` (SDD 07 SO-T34 to SO-T39).
- **The `arrow_ipc` sink's files open in pyarrow (KA11).** Every footer block's offset, metadata length and body length are multiples of 8, and the body length matches what the record batch message declares, as Arrow C++ requires; body buffers stay page-aligned. `pyarrow.ipc.open_file` reads the sink's output, ordered and unordered (SDD 08 SI-T27).
- **Compressed Arrow IPC is read safely and written on request (KA10).** ZSTD and LZ4_FRAME record batches are accepted wherever Moruna reads IPC. Every buffer's declared uncompressed size is checked against what the batch can need (from the column's type and length, and for string data its last offset, padded to at most the next 8 or 64 bytes) and against a ceiling before anything is allocated; decompression is bounded to that size, and anything else is refused naming the column and buffer, never a panic. The sink gains `compression` (`none`, `zstd` with `level`, `lz4`); 1,000,000 rows of 5 columns are 3.07× smaller with zstd. Staging and spill stay uncompressed (SDD 01 e.8, CT-T24 to CT-T27; 08; 07).

## 0.5.8

- **`moruna-job`: what an embedder depends on to know Moruna's kinds and check a job without running it (KA4).** A new crate holding the job document's types (`JobSpec`, `KindDoc` and every document type), the kinds' `Declaration` and its parts, and `Listing`, moved out of `moruna-runtime`, which now uses them from there; nothing is re-exported. `Catalogue::standard()` (and `standard_with_peql()`) reads the declarations of Moruna's standard kinds from files the crate carries, kept equal to the registry's listing by test; an embedder adds its own kinds with `Catalogue::add`. `moruna_job::check(job, catalogue)` returns every refusal, each naming its field: an unknown kind with the kinds known, settings that fail the kind's schema (a JSON pointer to the value), flows that do not fit, a kind that needs contracts with none carried. Settings are checked by a validator of the JSON Schema subset the kinds' schemas use; a schema outside it is refused when the kind is added. `moruna check-job <file>` runs the check from the command line. `job.digest()` is `moruna_runtime::job::digest(&job)` (SDD 22).
- **Malformed Arrow IPC is an error, never a panic, wherever Moruna decodes it.** A `.wasm` stage's output, a `.pex` stage's output, the staging records read back, the Parquet `ARROW:schema` footer and the trace view each check every message before arrow-ipc sees it; fuzzing found about a dozen arrow-ipc 59.3 panics on bad input and each is now refused with a sentence naming the fault. Compressed record batches are refused everywhere for now: arrow-ipc reserves the size a compressed buffer declares before decompressing it (SDD 01 CT-I13, e.8; 16 e.5; 17 SB-I14; PR 62).
- **Every started task is told `task_ready` before `task_started`, whatever the timing.** A producer pushed its first morsel and then told `Fed`; a consumer on another thread could take the morsel and tell its start in between, and the lifecycle then went from waiting straight to running and told no `task_ready`. A start while still waiting now tells ready first, a late `Fed` tells nothing, and each event is stamped under the lifecycle lock so `t_us` never runs backwards (SDD 12 PY-I12, PY-T28, PY-T29; PR 70).
- **The Linux wheels are built on ubuntu-24.04 and a wheel with no manylinux tag fails the build** (PR 63).

## 0.5.7

- **A source whose splits hold no rows finishes (MA1).** `SELECT 42 AS answer WHERE false` through a `datafusion` source waited until it was cancelled: its plan is one split with no rows, and the source drive's cursor stepped past such a split only when it took a range, which it never did, so Q0 never closed. The cursor now steps past every split it has no rows left in whenever it is read or advanced, so a plan whose remaining splits hold no rows is exhausted, and no read is issued for an empty split. A plan that ended in empty splits, or held nothing else, hung; one with an empty split between two that hold rows did not (SDD 10 f.5, SC-T24, SC-T25).
- **A source or sink that panics ends the run instead of hanging it (MA2).** A panic in a source's read, a sink's write or `finish`, or a drive's own code killed that drive's thread and the run waited for ever with no task ended. The drive now catches it and ends the run with a `Source` diagnostic naming the split, or a `Sink` diagnostic, saying what the panic said (SDD 10 h, SC-T26).
- **Every task gets exactly one end, whatever ends the run (MA2).** The task events of MH 4.3 already ended every task on a completed, cancelled or failed run; a run that unwound, or a lifecycle dropped before its end was told, told no end at all. A lifecycle dropped before its end now tells it: a cancel when the run was let go of (the scheduler's shutdown on drop is a cancel), a failure when a panic unwound it (below); an end is told once, the session's events are written on drop, the peer's thread no longer keeps the lifecycle alive, and the facade's record of what it started stops it on drop. Proved as properties: a cancel at every event of a run, by token and by the peer's message; a kernel failure at every apply under `terminate`, `skip` and `budget(2)`; a source that cannot be read; a run dropped at every point (SDD 12 PY-I11, PY-T23 to PY-T26).
- **A crash in Moruna fails its tasks with the new failure code `internal`; a run let go of is still cancelled. The `event` message is version 4.** A panic of Moruna's own on the run's thread (the session's, where the facade runs) ended every running task `cancelled`, as a run dropped by its embedder does. The session now catches it: every task still running gets `task_failed` with code `internal`, scope `task`, `retryable: false` and what the panic said as its `message`; when no task was running the attempt fails `internal` (`task: null`); a task that never started is skipped `attempt_failed`, and a cancel the run heard ends `failed`. The events are written, then the panic leaves `moruna run` and `moruna serve` as the panic it is, with no `report` or `exit`. A lifecycle dropped by an unwind no one caught fails the same way, saying the panic's words were not captured. A run dropped with no panic and no cancel still ends its tasks `cancelled`. `code` gains `internal`, so `event` is version 4 and a peer that reads only version 3 refuses it (MH 4.3; SDD 12 PY-I11, PY-T26, PY-T27).
- **A truncated or malformed Parquet file is a `Source` error, never a panic.** A file cut short after planning panicked with a subtraction overflow in the read's range arithmetic when a column chunk started past its end; each projected chunk's span is now checked against the file's length at plan and at read time, and the error names the split, the file, the row group, the column, the chunk's offset and the file's length. A negative chunk offset or size and an `ARROW:schema` the Arrow IPC reader would panic on are refused the same way, and a page request whose end overflows is the decoder's error (SDD 07 SO-I10, SO-T31, SO-T32).

## 0.5.6

- **A `.wasm` stage calls named ports and waits for their answers (MH 4.10).** The `moruna:kernel` world gains its second import, `call(port: string, request: list<u8>) -> result<list<u8>, string>`; Moruna reads none of the bytes. The job document's `kernels[].ports` lists, for one `.wasm` package stage, each name its `call` may use and where it goes: `{"host": "<name>"}`, answered by the host protocol's peer, or `{"guest": "<name>"}`, a handler the program embedding Moruna registers through `KernelLoader::guest_port`; `deadline_ms` bounds one call (absent: 30 minutes, at most a day). A host port rides the run's one connection as new messages, versioned on their own (v1): `port_call` out, `port_reply` in, and `port_cancel` when Moruna stops waiting (`deadline`, `cancelled`). The port's own refusal is handed to the component; an unlisted name, a request or answer past 64 MiB, a missed deadline, a lost answer and the run's cancel end the stage with the cause. The document refuses, by field, a host port with no peer, an unregistered guest handler, both places or neither, a bad name or deadline, and ports on anything but a `.wasm` package. A `.pex` calls no port.
- **A stage that waits on a port is waiting, not busy or idle.** The heartbeat keeps going; the task is told `task_waiting` with `reason: "port_call"` and the `port`, then `task_phase` when it works again; the scheduler counts `workers_waiting` and `stages_waiting`, and the controller classifies `Waiting`, moves no knob for it, keeps its target through a resize and does not end the run for its state. A stateful stage that lists ports keeps its state as each batch begins, and while it waits that is its checkpoint (`Kernel::waiting_state`), so a long wait no longer fails the checkpoint as busy.
- **`staging.url`: a run resumes on another machine.** Each manifest, once on disk, is copied to `<url>/moruna-<run_id>/manifest.json` before its write counts as done; a resume by `auto` or run id reads the copies into `staging.dir` first, so a run whose machine is lost resumes with an empty staging disk, its stateful stages restored. `moruna-reactor` gains `ObjectFiles` (whole-object put, get, delete, prefix listing).
- **The `event` message is version 3.** Version 1 was the task lifecycle (PR 54), version 2 added `logs` (PR 56), version 3 adds the port wait above. A peer refuses a version it does not read.
- **A task's output is captured where it leaves the task and kept in the run's output store.** stdout, stderr and logging records, attributed per task (`event` kind `log`), bounded and counted; the socket carries only cumulative counts (`logs` events). `.pex`, in-process Python, Rust (`moruna_kernel::output`) and Wasm (WASI stdout/stderr refused) each captured on their own terms (PR 56).
- **The engine reports each task's lifecycle to its host as it happens.** A new host-protocol message, `type: "event"` (envelope `v`, `attempt`, `start`, `seq`, `t_us`), sent between `hello` and `report`, carries `attempt_started`, `task_registered` (task, element, stage, upstream, members), `task_waiting` (reason, blocking), `task_ready`, `task_started` and `task_phase` (calibrating, reading, applying, writing, draining, committing), `task_completed` (outcome, duration, counters, cause), `task_failed` (code, safe message, scope, retryable), `task_skipped`, `cancel_acknowledged` and `cancel_ended`. The facts come from a `StageHook` in the scheduler on the thread where each becomes true; a source completes only when drained; adjacent standard kernels fused into one stage are one task listing its `members`. The job document gains `report.tasks` (opaque task ids) and `report.attempt`, neither changing its digest (PR 54).

## 0.4.0

The allocator guard: a Python kernel's own requests for memory are counted per call and refused at the ceiling, and the run report says how much of each stage's memory lived outside Arrow.

- **`memory_guard` on `@moruna.kernel`, default on.** While a Python kernel runs, a single request for memory (a NumPy array, a Python object) that would take the process past its memory ceiling is refused before the memory exists: the kernel sees `MemoryError`, and the run ends with a budget error naming the kernel and the request (`MorunaError::Refused`, the budget's exit code), rather than being killed at the ceiling. `memory_guard=False` turns refusal off for that kernel; what it asks for is still counted. The job document carries the same switch on a kernel stage, and `moruna check` reports whether each kernel's requests would be refused.
- **How the requests are seen.** CPython's three allocator domains (raw, mem, object) are hooked through PEP 445 and NumPy's data allocator through NEP 49, so each request is counted per call and can be refused; Arrow's requests are read from its memory pool's statistics, counted but never refused there (the arena's own accounting covers them). PyTorch and Rust allocations are not hooked.
- **Allocation counts on every trace record and per stage in the run report.** Each call's record carries what the kernel asked for; the report's `stages[..]["alloc"]` folds them per source (CPython, NumPy, Arrow): the number of requests, the bytes, the largest request, the peak, and the requests refused where the source can refuse. `outside_arrow_peak_bytes` and `outside_arrow_fraction` say how much of a stage's peak was memory outside Arrow, which is what a kernel's design should drive toward zero.
- **A refusal keeps the budget's exit code and follows the error policy.** A run whose kernel's request was refused ends as an over-budget run does, with the kernel and the request named; `moruna.MorunaError` carries the `Refused` kind in Python.

## 0.3.1

Vortex files as a source and a sink, with no decode copy for columns stored in a canonical encoding.

- **Vortex as a source.** `moruna.VortexSource(paths_or_prefix, columns=None, split_bytes=None)` and the Rust `VortexSource` read Vortex files, local or in an object store. The plan comes from the files' zone maps, so a split is a run of whole 8,192-row zones of about 128 MiB, its row and null counts are the file's own, and a fixed-width column's bytes are exact. A column the writer left in a canonical encoding is returned in the very arena buffer the reactor read it into, with no decode copy at all; compressed columns are decoded and copied into the arena once, as Parquet columns are. A read of any row range of any split is exact and repeatable, so runs over it can resume and spill.
- **Vortex as a sink.** `moruna.VortexSink(prefix, file_bytes=None)` and the Rust `VortexSink` write rolling `part-00000.vortex` files encoded straight into the arena, with the Parquet sink's commit, checkpoint and resume: a run killed in the middle of a file resumes and writes each row exactly once. A file rolls when the rows pushed into it reach the roll size, so `file_bytes` is a firm upper bound and a file of compressible data comes out smaller.
- The job document accepts `"kind": "vortex"` for the source (`options`: `columns`, `split_bytes`) and the sink (`options`: `file_bytes`).
- Adds the `vortex` 0.86.1 crates to the build (E2, 2026-09-29), with two supply-chain exceptions scoped to them: the 0BSD licence of `enum-iterator` and `enum-iterator-derive`, and the unmaintained-crate advisory for `paste`, a compile-time macro they use.

## 0.3.0

Sources and sinks of your own, written in Python, and correctness fixes across resume, the controller, the scheduler and Linux memory accounting, with a publish gate that ships only what was tested.

- **`moruna.Source`: a source of your own, in Python.** Subclass it with `plan()` returning `moruna.Split(id, rows, bytes=None)` for each split and `read(split_id, start, end)` returning exactly rows `[start, end)` of that split as a `pyarrow.RecordBatch`, and optionally `schema()`. Because `read` takes a row range, the source is sub-splittable and repeatable, so a run over it keeps look-ahead, Q0 eviction and resume, none of which `IteratorSource` can offer; a class whose reads are not deterministic sets `repeatable = False` and is treated as an iterator source is. A batch with the wrong row count or a changed schema is an `IoError` naming the split and the figures, and an exception in your code arrives with its Python message (SDD 07 e.6, f.7).
- **`moruna.Sink`: a sink of your own, in Python.** Subclass it with `write(batch)` and optionally `finish()`; each morsel arrives as a `pyarrow.RecordBatch` over the run's own memory, with no copy, and in order with `ordered=True`. Define `checkpoint() -> bytes` and `restore(state)` to take part in resume: a run killed mid-way and resumed delivers every row to your sink exactly once. A sink without `checkpoint` is not resumable, and the run report now says so (SDD 08 f.10, e.6).
- The report's note for a source that cannot be re-read now reads "source is not repeatable (an iterator source, or repeatable = False): no resume, Q0 staged", and a run whose sink does not checkpoint gets "sink: no resume, the sink does not checkpoint" (SDD 12 f.1).
- **A probe during a run measures its own morsel only.** The probe raised a gate that stopped workers picking, then waited for none to be busy, but a worker that had picked just before the gate went up could claim its slot after that wait and run beside the probe, so the peak memory and time the probe reported could include another morsel's. The gate is now part of the atomic word a worker claims its busy slot against, and a claim made after it is up is refused (SDD 10 f.9, amended 2026-09-30).
- **A lowered CPU limit is never exceeded by a task started after it.** A worker checked the bound before it picked and marked itself busy after, so a limit lowered in between let it start the task it had picked once the others had parked, and a worker still inside the bound could start one while a task from before the lowering ran: three workers busy under a limit of two for up to a task's length. The knob, the limit and the busy count now share one atomic word and a worker claims its busy slot against it with a compare-and-swap after the pick, so the busy count falls to a lowered bound as running tasks end and never climbs back over it (SDD 10 SC-I7 and f.2, amended 2026-09-30).
- **A peak reached before the machine shrank is judged against the ceiling it was reached under.** On macOS the report's peak is the kernel's lifetime mark, which the sampler reads rather than watches, so a peak from before a lowering could be read a few milliseconds after it and reported at 1.8 of a ceiling the run never ran under. The sampler now records the window the mark rose in (a record's peak has its `apply` as its window); when the ceiling moved or a drain began inside it, the peak is judged against the highest ceiling in force in that window, and the report's notes and its memory line say so, naming both ceilings (SDD 04 f.4, 03 f.2a).
- **A run on a machine that grows is not ended for having grown.** The controller took the limits each tick's sample carried, and a sample taken just before the machine grew carried the old ceiling: taken after the grown arena was reported, it left no room above the arena and a run could end with "footprint exceeds budget 0". A tick now keeps limits the watcher handed over after it sampled (SDD 11 f.15, RC-T19).
- **`moruna-vmm`: a refused vsock host stream ends cleanly on Linux.** A host that sent a bad `CONNECT` line to the monitor's Unix socket and more bytes after it (or whose connection the guest refused, or found no room) read `ECONNRESET` on Linux, where closing a Unix socket with unread bytes resets its peer; macOS gave end of stream. The monitor now shuts its side for writing and drains what the host still sends, up to 64 KiB and one second, before closing, so the host reads end of stream on every platform (MH 4.8.4, VM-T14).
- **`moruna-vmm`: the control socket's answer to an over-long request always arrives.** After answering a request line over 4096 bytes the monitor closed the connection at once, so a client still writing had its write refused, and on Linux one that had written past the line could read `ECONNRESET`. The monitor now shuts its side for writing and drains the client the same way (up to 64 KiB and one second) before closing: the client reads the error answer, then end of stream (VM-T18).
- **An explicit budget on Linux counts this process, not everything in its cgroup.** Where discovery found a cgroup it measured the cgroup's `memory.stat` whatever the budget was, so a run given an explicit budget in a container, or on a CI runner, was charged for every other process there: under `cargo test` it was charged for cargo's own 93 MiB and the test harness's parent, and 256 MiB runs were refused as below a floor of up to 360 MiB they had not made (`budget.host: ... The process held 272674816 bytes before the arena existed`). A Databricks driver's JVM would have been charged the same way. With an explicit budget, or a ceiling taken from the machine's RAM, the baseline, every sample and the report's peak are now the process's own anonymous memory (`RssAnon`, as macOS's `phys_footprint` is its own), and a note in the report says so; when the ceiling is the cgroup's limit the cgroup's figure stands, since the kernel enforces that limit on everything in it. File backed pages were never counted and still are not (SDD 03 DS-I4, DS-T15, DS-T16).
- **A safetensors file whose header was not padded reads correctly.** The reference writer pads the JSON header to eight bytes, so a tensor's data starts on an item boundary; a writer that does not pad can put a `float32` tensor at byte 91, and a `TensorSource` refused it (`byte offset 91 is not a multiple of the item size 4`). Such a range is now read from its own first byte, buffered, and the tensor is a view at offset zero. Found by the first end-to-end tensor job, which is now a test in the Python suite.
- **A shared cgroup's lifetime peak no longer sizes the run.** Where `memory.peak` cannot be reset (a cgroup the process may not write, as on a CI runner), it is the cgroup's peak since the cgroup was made, and a probe of a few hundred bytes was measured to cost everything the cgroup had ever held, so a run at any budget was refused as unsizeable. After a refused reset the sampler's own running peak is the peak.
- **A copy behind a slow sink no longer ends on a full arena.** A run with no kernel stage (a peQL plan into a contract write, say) read ahead of its sink until a read found the arena full, and the run ended with `alloc ... exceeds budget ... in use`: a queue over its high water that can evict is never counted full, nor is one waiting on an evicted head. It happened on a loaded machine, where the sink and a plan's re-reads are slow. The source drive now issues a read only when the arena has room for it beside the reads in flight, and issues no new read while an evicted entry waits to be read again, so the queue waits on the sink instead (SDD 10 f.5, SC-T22).
- **An unordered run resumes from any checkpoint it wrote.** A file sink fed out of order can commit a file holding sequence numbers on both sides of the point where everything below is committed (17, 18 and 20 in one file, 19 late in the next). The sink reported that point as its watermark, and a resume from it refused the checkpoint with "straddles the watermark", because keeping the file would have written row 20 twice; a SIGKILL resume test failed that way about one run in seventeen. The watermark now stops at the start of any committed file that straddles it, so a resume removes that file and replays its rows with the rest: every row still appears exactly once, at the cost of replaying up to about one more file. A checkpoint that genuinely disagrees with the store is still refused (SDD 08 f.7, SI-I8, SI-T17).
- **A Parquet run writes its `_SUCCESS` marker.** `finish` has always asked for the empty `_SUCCESS` object that downstream readers wait for, but the reactor treated a zero-length object write as nothing to do and resolved it without writing, so no run left the marker, on a local directory or an object store. An empty object is an object: the reactor now puts it (an empty file under `file://`), and every other zero-length operation still resolves at once (SDD 06 h, RE-T16; SDD 08 e.2, SI-T23).
- **`RunReport` has an attribute for every field of the report.** `limits_initial`, `limits_timeline`, `drains`, `cpu_ns`, `mem_byte_seconds`, `usage_measured` and `peak_ceiling_bytes` were in `to_json()` from 0.2.x but could not be read as attributes. They can now, and `limits` stays as another name for `limits_initial`.
- **Nothing is published untested.** A commit on `main` publishes to PyPI, as a tag or as the documentation site only when it is the merge of a pull request whose checks passed. 0.2.0 shipped from a commit that had not been through them.
- **The documentation is a site.** It is at [griot-cloud.github.io/moruna](https://griot-cloud.github.io/moruna/), with a quickstart, guides to Python, kernels, the command line and hosting, and a reference.

The report goes to `report.file` (where `<run_id>` is replaced by the run's id), or by default to `moruna-<run_id>.report.json` in the staging directory. The command is installed as the `moruna` console script and as `python -m moruna`.
- **`moruna serve --listen <address>` runs one job sent over a socket.** The address is `unix:///path`, or `vsock://CID:PORT` on Linux. Moruna sends `hello`, a `heartbeat` every second, `limits_changed` when the machine changes, the `report` and `exit`, as newline-delimited JSON; the peer may send `spec`, `cancel` and `checkpoint`, and nothing that sets a knob. If the peer goes away the run carries on and the report file is still written. `serve` is strict unless given `--no-strict`, and `report.socket` makes `moruna run` speak the same protocol to a peer.
- **The budget follows the machine it runs on.** Every controller tick re-reads the cgroup's `memory.max`, `memory.high` and `cpu.max`, or `/proc/meminfo` and the online CPUs inside a VM. When the ceiling falls the controller re-plans at once and the arena drains its newest regions; when the machine grows, the arena and the worker pool grow up to `budget.elastic.memory_max_bytes` and `budget.elastic.cpu_max`. A document with no `budget.elastic` never grows, and every run, elastic or not, follows its machine down. The report carries `limits_initial`, `limits_timeline` and each drain's duration, and `peak_fraction_of_ceiling` is measured against the ceiling in force at the peak.
- **A kernel can declare what it takes and gives, and `moruna check` tests it.** `@moruna.kernel` takes `input_schema=` and `output_schema=` (a `pyarrow.Schema` is exact, a mapping is a subset, and an output of `adds`, `drops` and `changes` is relative to the input), and `lockfile=`, which is folded into the kernel's fingerprint. `moruna check <module or file.py>` runs each kernel on seeded synthetic batches from its declared input, refuses one whose output disagrees (naming the column and both types) and exits 2, and otherwise writes the profile row the first real run sizes from. A kernel checked over a subset of columns now seeds a run over a wider source, with a note naming the schema it came from.
- **A function from a Polars frame to a Polars frame is a kernel.** A function annotated `pl.DataFrame -> pl.DataFrame` (or `pl.LazyFrame`) can be decorated directly, and `moruna.polars(fn)` takes the same declarations. The batch reaches Polars, and comes back, through the Arrow C data interface rather than `polars.from_arrow` and `to_arrow`.
- **Twelve standard kernels need no Python code.** `moruna.std` provides `cast`, `rename`, `select`, `drop`, `filter`, `fill_null`, `dedupe`, `hash`, `mask`, `explode`, `concat_str` and `date_trunc`, each built from its arguments with declared schemas, and a job document names them as `{"kind": "std", "name": ..., "args": ...}`. Adjacent `cast`, `rename`, `select` and `drop` run as one projection, and `filter` after `fill_null` as one pass.
- **A killed run resumes to what an uninterrupted run would have written.** Two ways a resume could lose morsels are closed: a read in flight at a checkpoint was in no manifest, so under an ordered sink the resume waited for ever, and a morsel the sink committed while the manifest was being taken could be in neither the watermark nor the lineage. Tested by SIGKILL at random points, then a resume in a fresh process compared with an uninterrupted run. A run into an unordered file sink could still refuse its own checkpoint about one time in seventeen, and 0.3.0 fixes that.
- **`resume="auto"` starts fresh when there is nothing to resume.** It resumes the newest manifest in the staging directory written by the same job (the same kernels, and from a document the same document), and otherwise starts a fresh run with a note, where 0.1.1 raised an error. It still needs a staging directory to look in. A job document declares a staging directory that survives the machine with `staging.durable`, the `checkpoint` message writes a manifest on request, and a resume under a different document is refused.
- **A governed peQL plan can be a source, and a write under a peQL contract a sink.** In the job document, `"kind": "datafusion"` reads what peQL plans for a caller over one contract or over SQL, and `"kind": "peql"` writes under a contract, by its owner only, refreshing the contract's manifest when the run finishes. The plan's operators run inside the run's budget, spilling to the staging directory, and are planned for the partitions their share can hold. A sink that resolves to the same files as its source is refused. These need a build with the `peql` feature: the guest image has it from 0.2.2 and the PyPI wheel from 0.2.4, and 0.2.0's builds refuse both kinds.
- **Object stores can be reached through a socket, for a machine with no network.** An S3 endpoint may be `unix:///path`, or `vsock://CID:PORT` on Linux, and Moruna speaks plain HTTP/1.1 over it to whatever proxy the host runs.
- **Parquet in an object store can be read.** The Parquet source could not read an object's footer, and a listing under `s3://b/in/` came back as keys under `s3://b/in/in/`, which nothing could read. Both are fixed.
- **The whole process stays under the ceiling, and the report measures it.** `peak_anon_bytes` and `peak_fraction_of_ceiling` are now the whole process's peak as the operating system counts it (`/proc/self/status` or the cgroup on Linux, the kernel's lifetime `phys_footprint` mark on macOS), so a run with no kernel no longer reports 0. From 0.3.0, a run on Linux with an explicit budget counts its own process rather than everything in its cgroup. What no pool accounted for is now bounded: peQL's write buffers, a plan's scans and operators, and a copy's heap decode each have a share of the budget, and a run with no kernel stage is stopped with a diagnostic before the process reaches its ceiling. On a loaded machine a copy behind a slow sink could still end on a full arena; 0.3.0 makes it wait for the sink. Measured on macOS at 256 MiB over six shapes of run (a contract write, a governed view, a copy, a view into Parquet, an aggregation and a copy with no kernel), the worst whole-process peak fell from 2.38 of the ceiling to 0.90.
- **A budget too small for a run is refused before anything is built.** The refusal names the run's floor and what it is made of: an arena of 64 MiB, 40 MiB for a governed plan, 16 MiB for a contract write, declared kernel state and the reserve, over what the process already held. It also says that a process which has just built and freed a dataset may be holding pages it can hand back.
- **The process uses the platform's allocator.** mimalloc is gone: it kept freed memory, up to 4.7 times the ceiling on the measured runs. On Linux with glibc, the first run in a process fixes glibc's mmap threshold at 256 KiB and its heap count at four, for the whole process, so freed buffers go back to the operating system.
- **The arena reuses freed memory at small budgets.** It now merges free neighbouring blocks, so a region cut into small pieces can serve a large request again, and the Parquet sink takes two buffers of at most a quarter of what is free when it opens instead of the largest the arena would give. A run into Parquet at 256 MiB that could not find an arena buffer now completes.
- **`moruna-vmm` runs Moruna in a microVM.** The monitor is built on the rust-vmm crates for Linux on x86_64 and aarch64, with virtio-blk, virtio-vsock, virtio-mem and a serial console, memory hot-add on both and vCPU hot-add on x86_64 (an aarch64 guest boots with all its vCPUs), and `boot`, `resize`, `status` and `stop` commands. It has no network device and no configuration field for one. `moruna run --vm <spec.json> --image <path> [--disk <path>[:ro]]...` boots the guest at the document's `budget.memory_bytes` and `budget.cpu`, which it requires, and exits with Moruna's code; off Linux it is refused by name.
- **The guest image and the monitor are release artefacts.** The guest image is Linux 6.18.54, a BusyBox initramfs and a read-only EROFS root with free-threaded CPython 3.14.7, pyarrow 25.0.1 and the Moruna wheel; its init runs one `moruna serve` over vsock and powers off. The image is built twice per release to show it reproduces, published to `ghcr.io/griot-cloud/moruna-guest` by digest (the `.ref` file on the release names it), and every artefact carries a `.sha256`, an SPDX SBOM and a keyless cosign signature. 0.2.0's guest image cannot start Moruna (see 0.2.1).
- The KVM boot, resize and network-isolation tests, and the tests under a real cgroup whose limits are rewritten, need `/dev/kvm` or a writable cgroup v2 and have not yet run in the release gate; they are tagged for the reference host. The elastic budget is tested through the watcher with a scripted machine.

## 0.1.1

Fixes S1 for tight budgets. **Do not use 0.1.0**: its memory bound could be exceeded by about a percent at a tight ceiling, it was published from a failing pipeline, and it carried a Linux wheel only. It is no longer on PyPI.

- **The memory bound holds at a tight ceiling.** The controller planned morsels into the whole of the headroom the arena leaves above itself, and the morsels are not the only thing there: a Parquet writer's encoder, the Arrow builders a batch is converted through and the interpreter's own growth are all outside the arena, none of them in the model, and every one of them in the figure S1 is measured from. A Python kernel at a 512 MiB budget on a host with a large resting footprint reached 1.005 and 1.012 of its ceiling. The kernels are now planned into a share of that headroom and the rest is held back (11 f.3), and the same job peaks at 0.976 across resting footprints from 0 to 380 MB.
- **A kernel's fixed cost is funded before its first morsel.** One probe cannot tell a kernel that holds a fixed cost from one whose cost scales with the morsel, and the model read its whole measurement as the scaling term, which under-predicted a constant-cost kernel by the ratio of the morsel sizes. The probe now seeds both terms until a record separates them.
- **A budget that cannot hold a run says so before the run starts.** Where the smallest morsel the runtime can form does not fit the ceiling, `start` refuses with the arithmetic it refused on. It used to begin, run one morsel and report a footprint the process was already holding.
- **macOS wheels.** 0.1.0 published a Linux wheel only, because the publishing step cannot run on a macOS runner. Building and publishing are separate jobs now, so both platforms ship.
- **`inspect_host()['anon_bytes']`**: what the process is already holding, measured the way the runtime measures it. A budget is a ceiling for the whole process and the arena is sized from what was resident before it, so this is the figure a caller needs to choose one. Pages a memory pool is holding for reuse count too: on Linux pyarrow allocates through jemalloc, which does not return them until asked, so `pa.default_memory_pool().release_unused()` before a run can be the difference between a budget that fits and one that does not.
- The run report travels with the Python surface's budget diagnostics, so a ceiling passed on a host you cannot log into is answerable from the report alone.

## 0.1.0

Withdrawn. First release: Parquet to Python to Parquet inside a byte budget, spill to disk, resume from a manifest, Polars and DataFusion bridges. Its memory bound could be exceeded by about 1% at a tight ceiling (see 0.1.1), and the wheel was Linux only.
