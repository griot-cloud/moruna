# 1.4: `platform`, instance data and node config

- **System design:** `architecture/moruna-os-system.md`, section 1D (with 1B and 1C).
- **Needs:** 1.2 and 1.3. **Rules:** `architecture/work/_rules.md`.

## Goal

The node finds its cloud, reads its config from instance data, sets its wall clock, hands `api` its
config, and says it is ready.

## Build

1. **The process.** New crate `kernel/node/platform`, package `moruna-node-platform`, a program on
   `moruna-svc`, account 16 MiB. Its HTTP/1.1 client is minimal: `GET` and `POST` (for Azure's
   report later), `Content-Length` bodies, no chunked transfer, no redirects, 1 MiB response limit.
   JSON through `serde_json` without std.
2. **The profile.** `cloud.image` gains `program:platform image.platform`. Additions to `node.conf`:

   ```
   service platform image.platform 16777216
   link network listen-platform platform network
   link platform api api platform
   ```

   Addition to `network.conf`:

   ```
   grant listen-platform rights=connect remote=169.254.169.254/32@80,168.63.129.16/32@80 sockets=4
   ```

   The supervisor starts `platform` after `network` and `api`. If a line is refused as written, ask.
3. **Finding the cloud and the config:** exactly as 1D says, in its order, with its retry rules and
   its 90 s deadline (`moruna: fatal instance-data: <reason>`).
4. **The wall clock:** the `Date` header of the answer that named the cloud, in IMF-fixdate form.
   One that does not parse is fatal.
5. **Node config v1:** exactly 1D's schema.
   - `token_keys`: 1 to 8 entries, each standard base64 of a 32-byte Ed25519 public key.
   - `tls`, when present: `certificate` holds one or more PEM `CERTIFICATE` blocks, and `key` one PEM
     `PRIVATE KEY` block. Deeper checks of them are `api`'s, in 2.2.
   - Anything else is refused, and every refusal is fatal: `moruna: fatal config: <reason>`.
6. **The hand-over.** New crate `kernel/node/config`, package `moruna-node-config`, holds the
   hand-over message as Rust types: the validated node config, the instance ID, the cloud, the wall
   clock (Unix seconds) and the monotonic time it was read. Sent as JSON over the `platform`-`api`
   link. `api` stores it, and answers `ready` once its listener is open.
7. **The lines.** `platform` prints `moruna: cloud <cloud> instance <id>` once config is valid, then
   `moruna: ready api=<address>:443 boot_ms=<n>` when `api` answers `ready`. `<n>` is the core's
   monotonic clock in milliseconds. Say in your report where that clock's zero is set.

## Testing

- **Fake instance data with no test hook in the node:** run QEMU's user network as
  `-netdev user,id=net0,net=169.254.169.0/24,host=169.254.169.254`. QEMU then forwards the node's
  connections to `169.254.169.254:80` to the host's loopback port 80, where a small test server
  plays OpenStack or Azure from recorded answers. If port 80 cannot be bound where the boots run,
  ask.
- Host tests: detection over recorded answers (Azure's `400` and `404` to OpenStack paths among
  them), every refusal in step 5, the date parser, and the hand-over's round trip.

## Success

- Booted against the fake OpenStack: the `cloud` and `ready` lines in order, after the network line.
- Booted against the fake Azure, with user-data base64-encoded: the same, naming `azure`. No ready
  report yet: that is 1.12.
- With no server: the instance-data fatal line by 95 s, then a power-off.
- Each invalid config gives its own `fatal config` reason in a booted run: no `token_keys`, nine
  keys, a bad key, an unknown field, a wrong version.
- 1 and 2 CPUs.

## Not yours

TLS in `api`, any API operation, Azure's ready report, the wireserver, cloud `none`.

## Report

The commits, the boot logs, where the monotonic clock's zero is, and `boot_ms` on each run.
