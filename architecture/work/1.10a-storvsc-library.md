# 1.10a: `moruna-storvsc`, the library

- **System design:** `architecture/moruna-os-system.md`, section 1F.
- **Findings to read:** `architecture/work/1.7-azure-findings.md`, section 3.
- **Needs:** 1.9a merged (the vendored crates). Host only. **Rules:** `architecture/work/_rules.md`.

## Goal

Azure's disk protocol, storvsc, as a library a driver process will wrap: it turns block reads and
writes into SCSI requests on a VMBus channel.

## Build

1. **The crate:** `kernel/drivers/storvsc/core`, package `moruna-storvsc`, `#![no_std]` with
   `alloc`, no unsafe code. It uses the vendored `storvsp_protocol`, `scsi_defs` and `vmbus_ring`.
2. **The channel:** the library is generic over `moruna-vmbus`'s `Channel` trait. That crate is
   being built in parallel (item 1.9b) and may not be merged. If it isn't, define the trait in
   your crate's `channel` module exactly as section 1F states it (the two rings, signal, wait, share
   memory), marked `// moruna: moves to moruna-vmbus (1.9b)`. The PM reconciles the two at merge.
3. **Initialisation,** in storvsc's order: begin, query the protocol version (offer the newest
   `storvsp_protocol` defines and step down), query properties, end. Follow OpenVMM's
   `storvsc_driver` as the reference for order and packet layout; cite the file in comments.
4. **Operations,** exactly what `moruna.driver.block` needs (`kernel/drivers/block-protocol`):
   - capacity and block size (READ CAPACITY 16);
   - read and write of a block range, as SCSI READ 16 and WRITE 16, the data named by guest page
     numbers the caller gives (the "GPA direct" packet form), so nothing is copied;
   - flush (SYNCHRONIZE CACHE);
   - the device's serial, from the VPD page 0x80 inquiry, for section 3C's volume names.
5. **Requests in flight:** up to the channel's limit from the properties answer, each matched to
   its completion by transaction ID. A completion for an unknown ID, a bad size, or a SCSI error is
   an error to the caller, never a panic. No sub-channels.
6. **A fake storvsp,** in the tests: the host's side over an in-memory `Channel`, backed by a byte
   vector as the disk, strict about order and sizes.

## Success

Host tests: initialisation including a version step-down; read-back of written blocks at the first,
last and a middle block; a range past the end refused; flush; the serial; 32 requests in flight
completing out of order; a SCSI error surfaced; garbage from the host refused without a panic; a
fuzz-style run of 10,000 random host packets with a fixed seed. 80% line coverage. Builds for the
user target.
