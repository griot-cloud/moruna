# 1.6d: imagefs looks up `system` before virtio-blk registers it

- **System design:** `architecture/moruna-os-system.md`, sections 1A (the image, the
  `moruna-system` partition) and 1B (boot, deadlines on boot waits). The device manager's
  directory: `kernel/devices/server/src/lib.rs` (SDD 25, d.6). **Rules:** `architecture/work/_rules.md`.
- **Found by:** Servercore run 8 (2026-11-18, image 381d1a46 + 1.6c's hold), the first console
  that shows the fatal line on real KVM.

## The miss

Servercore (KVM, q35, UEFI, 1 vCPU), console `~/moruna-data/servercore/run-8/console.fast`:

```
KB3 devices: started 2 drivers: net0 (virtio-net at 03:00.0), block0 (virtio-blk at 04:00.0); …
moruna: services started
KC2 imagefs: FAIL: looking up system: Remote(NotFound)
kk: process imagefs exited with code 1 (it ran on cpus 0)
KB3 block0: virtio-blk up: 33554432 sectors of 512 bytes, … the boot disk, its moruna-system partition …
moruna: fatal imagefs: ended with code 1
KB3 block0: registered as system
```

imagefs looked `system` up before block0 had registered it, and the directory answered
`NotFound` at once. Under QEMU's emulator, and on Azure, the order happened to go the other
way. This is a race in the boot, not a KVM fault. It decides whether a node boots at all.

**Where:** the directory makes a lookup of an unknown name wait while a held `register*` slot's
driver has not finished registering (`Registry::expect` and `Registry::finished`). The module doc
names the supervisor's drivers (`storvsc`, `netvsc`). virtio-blk also takes a `register*` slot
(`kernel/drivers/virtio-blk/src/main.rs`, the registration of serials and `system`), but it is
started by the device manager. Its registration is evidently not awaited, so a lookup made before
it registers fails.

## Do

1. **Write the defect as a host test** in the directory's library: a lookup of a name, made
   before a driver that holds a `register*` slot has registered it, is answered when the driver
   registers it, or with `NotFound` once the driver finishes, for every driver given such a slot,
   whoever started it. It fails today for a driver the device manager starts.
2. **Fix it in the directory,** with its one mechanism: every `register*` slot handed out, by the
   supervisor or by the device manager, is expected until its driver finishes registering. The
   wait stays bounded as it is today: a driver that ends finishes it, and a hang runs into the
   boot's deadlines. Update the module doc and SDD 25 if they state the narrower rule.
3. **Check every client** that looks a registered name up at boot (imagefs's `system`, the
   network server's `net0`, volumes by serial in 3.3) against the rule, and list them.
4. **A booted check** under QEMU, in a lock turn, that makes the old order happen: for example,
   delay virtio-blk's registration in a diagnosis build (`package.py --feature`, never shipped), or
   find a QEMU setting that gives the same order. It fails before the fix and passes after. Report
   the image command.
5. **The PM reruns Servercore** with the fixed image.

## Refused

A retry loop or a sleep in imagefs, or any client, in place of the directory's wait; a longer
timeout.

## Success

The host test and the booted check pass, and Servercore reaches `moruna: ready` with 443 answering.

## Report

The test, the fix, the client list, the booted check with its image command, coverage, and the
commits.
