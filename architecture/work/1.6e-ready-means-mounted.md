# 1.6e: `ready` waits for the engine's layer, and the disk list waits for drivers still registering

- **System design:** `architecture/moruna-os-system.md`, sections 1B (`ready` means the node can run
  a job; amended 2026-11-18), 1D (`platform`'s steps) and 3C (volumes by serial). The directory:
  `kernel/devices/server/src/lib.rs` (`Held`, from 1.6d). **Rules:** `architecture/work/_rules.md`.
- **Found by:** 1.6d's booted check (merged, fbacb6dd), image B. virtio-blk registered late
  (`register-late`, a diagnosis build):
  ```
  moruna: ready api=169.254.169.15:443 boot_ms=648
  KB3 block0: registered as system
  KC2 imagefs: up: 1 layers, lowest first: system (…); a cache of 4096 pages
  ```
  `ready` came about 10 s before the engine's layer was mounted. Had imagefs failed, the node
  would have reported ready, and on Azure sent the ready report, and then gone fatal.

## The two defects

1. **`ready` does not wait for imagefs.** 1B now says: `platform` prints `ready`, and on Azure
   sends the ready report, only after `api` answers and `imagefs` has mounted the engine's layer.
   The mount has the instance data's limit, so a node whose layer never mounts still ends in a
   fatal line.
2. **The directory's disk list (`blocks()`, directory minor 3) does not wait for held slots.** A
   job's check or launch right after `ready` could miss a volume whose driver is still
   registering, and refuse it as unknown. The list must answer only once every held slot's driver
   has finished (1.6d's `Held`), bounded as a lookup is.

## Do

1. **Write each defect as a failing host test:**
   - `platform` (or whatever owns the hand-over and the `ready` line) prints `ready` and sends
     Azure's report only after imagefs reports its layer mounted;
   - `blocks()` asked while a held slot's driver has not finished answers only after it finishes,
     and includes what it registered.
2. **Fix each with existing mechanisms:** imagefs's readiness reaches `platform` through a channel
   or signal the supervisor links, as `api`'s does. Name the one you use, and ask the PM before
   adding a protocol. The list waits on `Held` exactly as a lookup does.
3. **A booted check** under QEMU with `--feature virtio-blk/register-late` (1.6d's), in one lock
   turn: `ready` comes after `KC2 imagefs: up`, and `boot_ms` includes the wait. Also run one plain
   image, so the ordinary boot's `boot_ms` shows what the wait costs, if anything.

## Refused

A sleep or a poll loop; printing `ready` early and correcting it later.

## Report

The two tests, the fixes, the booted lines, coverage, and the commits.
