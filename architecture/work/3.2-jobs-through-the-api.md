# 3.2: Jobs through the API

- **System design:** `architecture/moruna-os-system.md`, sections 3A and 3B.
- **Needs:** 2.2b. **Rules:** `architecture/work/_rules.md`.

## Goal

A client submits a job over HTTPS, the node runs it in a fresh engine, and the client sees it
through to its report.

## Build

1. **Types:** 3B's operations, bodies and answers added to `moruna-api` (2.1), with the OpenAPI
   document, the MCP tool list and the Python client regenerated.
2. **Server:** the routes in `moruna-api-server`, over a trait, `EngineHost`, that the node's `api`
   program implements: check a document, start a job with its `spec`, send `cancel`, and receive
   the host protocol's messages. `api` does not link `moruna-job` (3A): validation is the
   engine's. Server-Sent Events are added to the HTTP layer here.
   - **Phase 1,** on the host: types, routes, state, redaction and SSE, tested against a fake
     engine in the tests that speaks `moruna-hosted-engine.md` 4.3 (`hello`, `heartbeat`, NUL-framed
     event records, `report`, `exit`, and a refusal with exit code 2).
   - **Phase 2,** booted: steps 3, 4 and 7.
3. **`api` as the engine's host:**
   - `node.conf` links `api` and `node-admission` (job and cancel requests);
   - `node-admission` starts the engine with a channel whose other end goes to `api`;
   - `api` speaks `moruna-hosted-engine.md` 4.3 on it, unchanged: `spec`, `cancel`; and it reads
     `hello`, `heartbeat`, the NUL-framed event records, `report` and `exit`.
4. **The engine's transport:** `moruna serve` gains `--listen channel:<slot>` beside `vsock://`.
   Nothing else in the protocol changes.
5. **State in `api`:** the last 100 jobs, with each one's latest heartbeat, exit and report, and a
   buffer of the last 100,000 event and log records for `events?from=`.
6. **Secrets:** 3B's redaction, with a test that a credential put in a job appears in no answer,
   event, log or report.
7. **The profile:** the step-3 services of 1A join `cloud.image`: `storage`, `imagefs`, `linux`,
   `node-admission` and `engine`, configured as `configure.py` configures them for the standalone
   node, less the vsock and launcher pieces.

## Success

On a booted node (`uefi-boot.sh`, fake OpenStack, test token):
- a job with a generating source and a counting sink validates, is submitted, runs, streams its
  events over SSE, and its report reads the right row count;
- a second submit while it runs answers `busy`;
- a long job is cancelled, and its state reads `cancelled` with exit code 130;
- an invalid job is refused at `validate` with `moruna-job`'s refusal and its field;
- the redaction test passes;
- 1 and 2 CPUs.

## Not yours

Volumes (3.3), the network for jobs (3.4), functions (3.6).

## Report

The commits, the boot log, and each check's output.
