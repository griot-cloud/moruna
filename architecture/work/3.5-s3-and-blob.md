# 3.5: S3, then Azure Blob, over `moruna-net`

- **System design:** `architecture/moruna-os-system.md`, section 3D.
- **Needs:** 3.4. **Rules:** `architecture/work/_rules.md`.

## Goal

A job reads its sources from, and writes its sinks to, S3-compatible storage and Azure Blob, through
the node's network server.

## Build

1. **Two object stores over the connector.** The engine's object-store settings accept `s3://` (any
   S3 API endpoint, path-style or virtual-host) and `az://` (Azure Blob). They are built with the
   `object_store` crate's `AmazonS3Builder` and `MicrosoftAzureBuilder`, with 3.4's `moruna-net`
   connector as their HTTP client. No source or sink changes: they see an `ObjectStore`, as
   `moruna-hosted-engine.md` 4.6 says.
2. **Credentials by secret name only.** S3: an access key ID and a secret key. Blob: an account key
   or a SAS token. The document carries `{"secret": "<name>"}` and the node's secrets (3.2) resolve
   it. A value never appears in a document, a report, an event or a log line; an error names the
   secret, never its value.
3. **Egress.** The host names 3.4 mints for a job come from these settings: the S3 endpoint's host,
   or `<account>.blob.core.windows.net`. Nothing else.

## Success

On a booted node under QEMU's user network, in one lock turn:
- **S3:** MinIO, run inside `moruna-arm` for that turn, over HTTPS with a test root added to
  `tls.roots` for that boot only. One NYC taxi month read from one bucket; the Score job written to
  another; rows and canonical hash as 0.6.6's for that month (`bench/vm/canon.py`).
- **Blob:** the same with Azurite (Microsoft's Blob emulator, from npm inside `moruna-arm`) over
  HTTPS. If Azurite can't run there, stop and ask.
- A wrong key fails with the store's error naming the secret, not its value.

Real Blob in `griot-dev` is the PM's check, with 1.13.
