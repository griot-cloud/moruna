# 0.1: A base that boots

- **System design:** `architecture/moruna-os-system.md`, section 0.
- **Needs:** nothing.

## Goal

Show whether the head of `feature/arrow-core-0.7` boots. It carries a new Linux layer that was
merged without ever being booted. You find out and report; you fix nothing here.

## Build

1. Build the boot image exactly as CI's kernel job does: `kernel/tools/build.sh` with
   `kernel/initramfs/boot.image` (`.azure-pipelines/ci.yml`, the kernel job).
2. Boot it with `kernel/tools/boot.sh` on 1, 2 and 4 CPUs, and judge each serial log with
   `kernel/tools/check-boot.sh`, as CI does.
3. If any check fails, find the first line that differs from `expect`, and which commit after tag
   `gate-verified-2026-11-17` introduced it (`git bisect` between the tag and the head).

## Success

- Either: `check-boot.sh` passes on 1, 2 and 4 CPUs at the head, with the three logs kept.
- Or: a report naming the first failing check, the commit that introduced it, and the serial log
  around the failure. Then stop. The PM decides whether that change is fixed or set aside.

## Not yours

Reverting, fixing or rewriting anything. Speed. Any file outside what the build writes.

## Rules

- Your branch starts from `feature/arrow-core-0.7`. Local commits only, with the trailers
  `Signed-off-by: Moruna Agent <agents@griotdata.com>` then `Co-Authored-By`. Never push.
- This Mac is arm64: x86_64 boots run under QEMU's emulator and are slow. Give `boot.sh` 900 s.
- Builds and boots on the Mac need `~/.vm-lock` (`tools/proof-lab/run.py` shows how to take it).
  Never steal it. Keep a VM at or under 6 GiB. Release it the moment you stop.
- The disk is nearly full: build with `CARGO_INCREMENTAL=0` and delete `target` when you stop.
- Where this document and the system design leave a choice open, ask the PM. Do not choose.

## Report

What passed, what failed and where, the commit if one is at fault, and how long each boot took.
