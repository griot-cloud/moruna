# 6.3ab: the node reads from its stores at about 55 MB/s however many requests are in flight

- **System design:** `architecture/moruna-os-system.md`, sections 1F (Azure, VMBus, netvsc) and 3D
  (the job's network), and SDD 31 (the network server). **Rules:** `architecture/work/_rules.md`,
  and 6.3's steps: measure, name the cause, write it as a test where it can be, then **stop and
  report** with the fix proposed and its alternatives.
- **Found by:** runs 7 and 8b (benchmark log).

## The evidence

Every job reads the same 843 MB in 139 requests.

| Run | Requests in flight (Occupancy) | MB/s a request | Node total |
|---|---|---|---|
| 7 | about 2.4 | 23–28 | about 55 MB/s |
| 8b (6.3y) | about 11 | 4.7–6.2 | about 55 MB/s |

- **The total does not move with concurrency.** What bounds it is the node's network path, not a
  request, a window or the engine's read-ahead.
- **Writes follow the same pattern:** about 10 MB/s a part either way.
- **Linux on the same VM size reads the year at about 300 MB/s.** That is the plain Rust pool and
  0.6.6's Rust function, in 2.8 s.
- **Under Score's computing, the rate per request falls further** (3.7 MB/s in run 8b).

The path a byte takes to the engine:
- Azure's host;
- VMBus and netvsc (`kernel/drivers/netvsc`, the vmbus process);
- the network server (`kernel/net/stack`): smoltcp's TCP, then rustls's decrypt with ring's
  AES-GCM, built for `x86_64-moruna-user` with `+sse,+sse2` only. ring picks its assembly at run
  time, so whether AES-NI is in use is a question to answer, not to assume.
- the IPC to the engine (`moruna_storage::net`, 64 KiB chunks);
- the engine's HTTP and the arena copy.

Nothing on the node reports where the time goes: the job's report has no figure from the network
server, netvsc or the vmbus process.

## Do

1. **Count, cheaply and always on.** Where each stage's bytes and nanoseconds can be read:
   - the network server: bytes in and out, its own CPU time, and the time in TLS decrypt and
     encrypt, in smoltcp's poll and in the copies to and from its clients;
   - netvsc: frames and bytes each way, receive-ring waits, interrupts or signals.

   Give them to the job's record or the node's `KB` lines, so a benchmark run carries them. Cost
   at most a clock read per batch of work, never one per packet.
2. **Measure on Azure, in one PM-approved run of the node alone** (give the PM the image and the
   plan): one 1 GiB object read at 1, 4, 16 and 64 connections. Also give the same reads with
   `curl` (or `object_store`) on a Linux VM of the same size, for the host's figure.
3. **Name the cause:**
   - CPU in TLS (and whether ring took its AES-NI path);
   - the network server's single thread;
   - netvsc's receive path;
   - the IPC copies;
   - or something else the counts show.

   Write it as a test where the code can show it on a host.
4. **Stop and report** with the fix proposed and its alternatives. Say for each:
   - what it costs;
   - how it stays the same on the host, the VM and the microkernel.

## Refused

- A larger TCP window or more connections as the fix before the cause is named: run 8b shows
  that concurrency does not move the total.
- A benchmark-only path.

## Report

The counts, the Azure figures with Linux beside them, the cause, any test, and the proposed fix
with its alternatives.
