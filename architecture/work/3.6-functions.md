# 3.6: Functions through the API

- **System design:** `architecture/moruna-os-system.md`, section 3E (and 1D's `functions`).
- **Needs:** 3.4. **Rules:** `architecture/work/_rules.md`.

## Goal

A signed function image is registered through the API and runs in a job; anything unsigned or
altered never runs.

## Build

1. **Types and routes:** `POST /v1/functions` (admin) and `GET /v1/functions` (observe) in
   `moruna-api` and `moruna-api-server`, exactly as 3E says, regenerated as in 3.2.
2. **Registration** checks the signature against node config's `functions.keys` and stores the
   entry in `api`'s memory. Nothing is fetched.
3. **At job start,** each function the job names by registered name is fetched through the job's
   network (3.4), from its `address`, and its SHA-256 is checked. The verified image goes to the
   engine as the image stage's image, as a local image does today. The cache follows `cache_bytes`
   and evicts the least recently used.
4. **Validation** refuses an unregistered name.

## Success

On a booted node:
- a registered native Rust function (one of `images/gate/functions`) runs in a job and its rows
  match;
- a registration with a bad signature, or signed by a key not in node config, is refused;
- an image changed after registration (served altered by the test server) is refused at job start,
  and the job fails naming it;
- a second job with the same function doesn't fetch it again.

## Report

The commits, the boot log, and each check's output.
