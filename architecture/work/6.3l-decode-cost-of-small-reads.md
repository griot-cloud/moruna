# 6.3l: decode CPU grows by half when the arena halves the reads' size

- **System design:** `architecture/moruna-os-system.md`, section 3A (the arena bounds how far
  reading runs ahead, never how many workers decode; a read that does not fit is cut to the room
  left). **Needs:** 6.3a, 6.3b, 6.3c (merged). **Rules:** `architecture/work/_rules.md`, and 6.3's
  steps: diagnose, write the defect as a test, then stop and report before fixing.
- **Found by:** 6.3d's measurements (2026-11-18), on the Mac.

## The miss

The year (NYC 2024, 12 files) copied Parquet to Parquet, 672 MiB, 4 workers:

| Arena | Reads | Decode CPU | Wall |
|---|---|---|---|
| larger (before 6.3d) | 744 | 3.25–3.35 s | 4.40–4.46 s |
| 265 MB | 1,480 | 4.96 s | 4.83–4.86 s |

The rename/select month at 672 MiB shows the same: with the arena at 420 MB against 630 MB, the
source makes 53 reads against 31, and decode CPU goes from 580–640 ms to 890–926 ms.

The same bytes are decoded either way. Twice the reads should not cost half as much decode work
again, unless something is done once per read that should be done once per row group or per
column chunk. Candidates: a dictionary page decoded again for each sub-read, metadata and page
headers parsed again, a decoder or a decompression context made per read, or buffers allocated
and zeroed per read.

## Do

1. **Reproduce it** with the command 6.3d's agent gives. Vary only the read size (the arena) and
   keep everything else fixed.
2. **Profile decode** at both sizes, per read and per row group: where the extra CPU goes, with
   numbers per candidate above.
3. **Write the defect in general terms** as a failing test: decoding a row group in k reads costs
   no more than a stated small overhead above decoding it in one. Take the overhead from what is
   unavoidable, and say what that is.
4. **Stop and report** with the fix you propose.

## Refused

A larger arena as the answer; a read size tuned to NYC.

## Report

The profile, the cause with file:line, the test, and the proposal.
