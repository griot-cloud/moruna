# 6.3f: on Linux, an image function also runs as one process however many CPUs the job has

- **System design:** `architecture/moruna-os-system.md`, section 3E (a function runs one instance
  per CPU of the job unless it declares fewer) and 3A. **Rules:** `architecture/work/_rules.md`.
- **Needs:** 6.3e's shared rule, `moruna_adapters::instances` (commit 592c32e6 on
  `work/6.3e-function-runs-alone`): `cpus`, `declared`, `count`, `fund`, `short_note`. Branch from
  that commit and rebase when 6.3e merges.
- **Why:** Moruna behaves the same on a host, a VM and the microkernel. 6.3e fixes the node. The
  Linux image kind (`crates/moruna-sandbox`, `ImageKernel`) has the same defect.

## The defect

`ImageKernel` holds one process and one stage cgroup per kernel:
- one `ImageMemory.cgroup`;
- `stage_limits` gives that process the run's whole remainder;
- `limits_changed` and `Drop` are keyed to that one cgroup;
- `kind()` is fixed at 1.

## Do

1. **Write the defect as a test** (Linux, delegated cgroup v2): an image function that declares
   nothing, in a job with 4 CPUs, runs 4 instances and its batches go to all of them.
2. **Build the rule with the shared module:**
   - the count is `instances::count(Context::cpus(node), instances::declared(env))`;
   - the memory bound is `instances::fund`;
   - the stage has one cgroup that carries the stage's ceiling (memory.max, cpu.max), with one child
     cgroup per instance under it;
   - outside memory is summed over the instances;
   - the limits are rewritten for all of them.

   `crates/moruna-kernel/tests` compile `moruna-micro/src/layout.rs` and
   `moruna-runtime/src/native_account.rs` on their own, so those two files must not reference
   `moruna_adapters`.
3. **Tests run in `moruna-arm` under the VM lock** (the sandbox is `cfg(target_os = "linux")`): the
   new test, the sandbox's existing suite, and coverage of the added lines there.
4. **A before/after table** in `moruna-arm`: a month of Score through an image function at 4 CPUs,
   with wall and the instances' busy peak.

## Report

The test, the build, the suite's result, coverage, the table and the commits.
