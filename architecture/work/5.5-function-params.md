# 5.5: A function reads its params the same way, native or image

- **System design:** `architecture/moruna-os-system.md`, sections 3E (functions) and 5 (the runtimes and SDKs). **Needs:** 3.6, 5.0–5.4 (merged). **Rules:** `architecture/work/_rules.md`.

## Why

An image function's process gets `MORUNA_ENTRY`, `MORUNA_ROLE`, `MORUNA_PARAMS` and `MORUNA_ARGS` (JSON objects, `docs/images.md`). A native function is refused params: `crates/moruna-runtime/src/kinds/function.rs`, `NATIVE_TAKES_NO_PARAMS`, says "a native function is started with no environment". So a job can't pass a threshold or option to a native function, and each SDK would have to know which kind it runs in.

## Build

1. **Native functions get the same four variables** in their process environment, as image functions do. Find the way the kernel starts a process (the start block that std on Moruna, with its one `_start` and relibc, reads for `std::env`), and give it the environment. Remove `NATIVE_TAKES_NO_PARAMS`.
2. **Each SDK has one accessor** that reads them in either kind:
   - Rust: `moruna_function::params()`, returning the parsed JSON, plus `args()`;
   - C: `moruna_params()`, the JSON string;
   - Python: `moruna.params()`.

   Document them where each SDK documents its functions.
3. **Tests:**
   - host tests of the runtime's handover for both kinds;
   - each SDK's accessor;
   - a booted check in CI's boot image: a native function given `{"threshold":0.5}` reads it and passes it back through its output. It runs in one lock turn when the PM names you in `~/.vm-lock-next`.
4. Update the job catalogue's descriptions that say native functions take no params.

## Report

The commits, the tests, coverage, and the booted check's line.
