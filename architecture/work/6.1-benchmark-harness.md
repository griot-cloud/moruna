# 6.1: The benchmark harness in griot-dev

- **System design:** `architecture/moruna-os-system.md`, section 6.
- **Needs:** 1.13 and 3.5 merged for a real run. The harness and its dry run need nothing.
  **Rules:** `architecture/work/_rules.md`; creates resources in `griot-dev` only.

## Build

`bench/node/`: one command on the Mac, `bench/node/run.py --plan <plan>`, which:
1. creates the resource group, the Blob container with the data, the Moruna node (the VHD, through
   `AZURE.md`'s steps), and one Linux machine for the other engines, each on `Standard_D4s_v4` in
   zone 3;
2. runs each job on each engine as 6B says, through the API for Moruna and over `az vm run-command`
   for Linux;
3. collects the results into `bench/node/results/<date>/` and the table into
   `architecture/benchmark-log.md`;
4. deletes the resource group, always, even on failure.

Reuse `bench/vm/` (the plans, `canon.py`, the report) where it fits.

## Phase 1 (now): no cloud resources

Brackly: create nothing until the OS is ready to test. So in phase 1:
- `--dry-run` prints every `az` command and every engine command, in order, and creates nothing;
- the parts that run on the Mac are tested against fakes: plan parsing, the result collector, the
  table writer and the root-cause log format;
- the Linux engines' install and run scripts (0.6.6, the Rust pool, DuckDB, Polars, Ray, Spark,
  Dask) are written from `bench/vm/` and checked by running each engine's Score job on one month of
  NYC data on the Mac, where the engine installs there with `uv`. The data is at `~/moruna-data/nyc/`
  once item 3.1's agent has fetched it.

## Success

- Phase 1: the dry run's command list for a full NYC plan, the fake-backed tests passing, and
  each engine's script giving 0.6.6's rows for the month on the Mac (or a note naming what couldn't
  run there).
- Phase 2, when 1.13 and 3.5 merge: the first real run, PM-approved.
