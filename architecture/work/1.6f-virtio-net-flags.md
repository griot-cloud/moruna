# 1.6f: virtio-net drops a received frame whose header carries a flag

- **System design:** `architecture/moruna-os-system.md`, sections 1A (virtio-net and virtio-blk on
  OpenStack), 1C (network) and 1D (instance data). **Rules:** `architecture/work/_rules.md`, and
  6.3's steps for the diagnosis part.
- **Found by:** Servercore run 9 (2026-11-18, image 5c7a32f1, the first boot past 1.6d's race).

## The miss

Console `~/moruna-data/servercore/run-9/console.fast` (KVM, q35, UEFI, 1 vCPU):

```
KE2 netstack: wan: DHCP bound 192.168.77.119/24, router 192.168.77.1, … 55 ms after the server started
moruna: network wan 192.168.77.119/24 gateway 192.168.77.1
moruna: fatal instance-data: nothing by 90 s: GET /openstack/latest/user_data: the deadline passed
KE1 net0: served until every client left: 36 frames out (3625 bytes), 23 in (3587 bytes), 46 malformed from the card
```

46 received frames were refused as malformed against 23 accepted. The metadata service never
answered. `kernel/drivers/virtio/src/net.rs` `received` refuses a buffer whose header has any
`flags` or `gso_type` (`NetError::Offload`), and the driver counts every refusal as one number.

**The likely cause, to be confirmed:** under KVM, vhost-net and tap set
`VIRTIO_NET_HDR_F_DATA_VALID` on frames whose checksum the host already trusts, for example frames
from the host's own namespaces such as Neutron's router and metadata proxy. They do it even when the
driver did not negotiate `VIRTIO_NET_F_GUEST_CSUM`. Linux's virtio_net accepts the flag. QEMU's
emulated path (TCG, slirp), which 1.6b's reproduction used, never sets it. The DHCP replies happened
to pass.

## Do

1. **Count refusals by reason,** in the production driver, not only in a trace:
   - a length out of bounds;
   - each flag value;
   - each GSO type.

   The `served until` line names them. Print the first refused frame's header bytes and length once,
   on the console. A boot that drops frames then says why.
2. **Write the defect as a host test** in the virtio library: a frame with `DATA_VALID` (2) set is
   delivered. Then decide by the spec and by what Linux does, and report the reasoning:
   - `DATA_VALID`: deliver. The stack verifies every checksum itself.
   - `NEEDS_CSUM` (1), which a device should not send without `GUEST_CSUM`: either complete the
     checksum in software from `csum_start` and `csum_offset`, or refuse it and count it. Which one,
     and why.
   - Any GSO type, which needs a GUEST_TSO/UFO feature we never offer: refuse and count.
3. **Fix it** in `received` and the driver, with tests for each case at 80% or more.
4. **Give the PM the image command** (the production cloud qcow2, `--node-memory 2147483648`) for
   Servercore run 10. The PM runs it and reads the reasons line.

## Refused

Turning off the stack's own checksum checks; negotiating offloads to make the flags legal (a
separate decision, not this item).

## Report

The reason counts, the test, the decision for each flag with its reasoning, coverage, the commits
and the image command.
