# 1.11b: The `netvsc` driver process

- **System design:** `architecture/moruna-os-system.md`, sections 1C and 1F.
- **Needs:** 1.9c and 1.11a merged; 1.3 merged. **Rules:** `architecture/work/_rules.md`.

## Build

`kernel/drivers/netvsc/server`: a driver process that opens the synthetic network card's channel
through `vmbus` and serves `moruna.driver.net` with `moruna-netvsc`. The network server sees it as
`net0`, so 1C's `network.conf` is unchanged.

## Success

On Azure (as 1.9c, with a public address and an inbound rule for 443 from the operator's address
only): the node's `network` line shows its DHCP lease, and a TCP connection from the Mac to 443 is
accepted. The network driver conformance suite (`kernel/drivers/net-test`) passes against it.

## Cloud

You create nothing. Finish the host part (host tests against `moruna-vmbus`'s fake host, at the 80%
floor), save the cloud image (VHD) from your lock turn, and report. The PM runs the Azure boot and
sends you the serial log to judge.

## DMA

Your process gets its own whole copy of `root.dma` (1F's Hyper-V DMA rule). Pin a client's memory
as `kernel/drivers/virtio-blk` does; long-lived buffers go through `vmbus`'s `share`.

## Report

The commits, the host tests, and the saved image's path.
