# 6.3r: a function run as several instances fails jobs on the node

- **System design:** `architecture/moruna-os-system.md`, sections 3E (one instance per CPU of the
  job), 3A (a function's memory is measured, never assumed) and 6. **Rules:**
  `architecture/work/_rules.md`.
- **Found by:** 6.2 run 4 (2026-11-18, image cdb5a7a1, which is 6.3e merged), on an Azure D4s_v4 node
  with a job budget of 4 CPUs and 12.98 GiB. The records are in
  `/Users/brackly/Desktop/Projects/moruna/.claude/worktrees/bench-run4/bench/node/results/202611181759/node/*.job.json`.
  Read them; never write there.

## The miss

6.3e works where it ran: Score's 3 passing runs took 53.0 s, against 93.2 s for one instance. But
the same rule fails three ways:

1. **Score, 2 of 5 runs:** `kernel stage 1 morsel 53: image gate-score@…: a record of 14884864
   bytes does not fit its input region, which has 13586432 bytes free and nothing to release`.
2. **Enrich, 5 of 5 runs:** `image gate-enrich@…: it said a batch was done without a record for
   it: a task answers every batch, with a record of no rows when it keeps none; it wrote nothing
   to its standard error`. The morsels differ from run to run (621, 3515, …).
3. **Enrich, one run:** `kernel stage 65535 morsel 18446744073709551615: image gate-enrich@…:
   previous task account has no certified retirement`.

The report says `function gate-enrich: a native program … 4 instances, one per CPU of the job`.

**Where:**
- Each instance's plane comes from its share of the stage: `layout::native_split(share)` gives it a
  quarter of the share. `ring_sizes` derives the piece, the input region (`(IN_FLIGHT+1) × piece`)
  and the output windows (`1.5 × piece`) from that budget. Funding 4 instances divides each share,
  and so the region, by up to 4.
- The batch the engine offers is cut by `layout::cut` against the piece. The record laid out in
  `offer_timed` (`crates/moruna-micro/src/task.rs`) then waits for room in the region, and fails
  when the task holds nothing it can release.
- `answers_timed` raises error 2 when the task releases the batch with no part put. Enrich's output
  is larger than its input (about 1.17 times, before framing). Whether the function's SDK (Rust,
  `kernel/function/rust/src/lib.rs`) drops an answer that does not fit its window, and then
  releases, is the first thing to find.
- Error 3 is raised in `ImageTask::start` when an instance's previous account or failure is still
  held. That is the case for an instance started again after a failure, or for one funded after
  another retired.

These are three readings to confirm or refute, not the answer. Find the root of each.

## Do

1. **Write each failure as a host test**, at the node's sizes: 4 instances, a 12.98 GiB job, and
   Score's and Enrich's batches (the scheduler's native-stage model, as
   `sc_p_native_stage_memory.rs` and `sc_p_a_function_runs_per_cpu.rs` do). Each test fails today.
2. **Fix each at its root:**
   - A record the engine offers an instance always fits that instance's region. A batch is cut to
     the instance's real piece, whatever the number of instances.
   - An answer that does not fit its window is never reported as done. The SDK either puts it in
     parts (the plane joins parts today) or fails the batch, naming the record and the room it
     lacked. Every SDK with this path follows the same rule: Rust, C and the Python shim.
   - An instance's account is retired, and certified, before the instance is started or funded
     again.

   If a fix needs a choice that 3A, 3E or this item leaves open, ask the PM.
3. **Show the rule holds at every count:** the tests from step 1 at 1, 2, 4 and 8 instances, with
   the region and windows each instance gets.
4. **Booted check under QEMU**, in a lock turn: one month of Score and one month of Enrich, at
   4 CPUs, each with real data and its output checked against the host's. The 6.3e booted check
   did not catch this because it used small batches. Report the image command.
5. **The PM reruns the node benchmark** with the fixed image.

## Refused

- Funding 1 instance, or any fixed count, in place of the fix.
- A larger fixed region or piece, chosen so that the benchmark's batches fit.
- A retry of a failed offer or answer.

## Report

For each failure: its test, its root and its fix. Also the per-count table, the booted lines with
the image command, coverage, and the commits.

## Leads (read from the code, 2026-11-18; not yet confirmed by a test)

**1. Score: the record does not fit.** The plane is probably not cut by 4: the share is capped at `NATIVE_CHILD_MAX`, so the piece is `PIECE_MAX` (16 MiB) and the region 64 MiB.
- The region's allocator is first fit (`kernel/plane/core/src/ringed.rs` `RegionRec::reserve`). The error's `free` is the largest free span, not the total.
- `offer_timed` gives up as soon as `step()` returns false. `step()` returns false after `LOOK_NS` (250 ms) with no event, even while batches are in flight.
- `step()` sets Puts aside in `early` and never calls `reap()`. Two answers kept in place (`keep_in_place`) plus one Put not taken fill all 3 windows. The task cannot answer, so it never releases, and the offer gives up.
- r1 and r4 both failed at morsel 53, with the same sizes.

**2. Enrich: done without a record.** The SDK's path for an answer that does not fit its window (`1.5 × piece`) has not been read yet: Rust in `kernel/function/rust/src/lib.rs`, then C and Python.
- After this error, `failed()` waits up to `END_SECONDS` (60 s) for the task to end, and the worker is held all that time.

**3. Enrich r3: no certified retirement.** `instances::release` (`crates/moruna-scheduler/src/instances.rs`) marks the slot free before the old `TaskState` drops.
- `held` drops after the lock guard. Another worker can then run `start` while `TaskState::drop` (kill, wait, retire within 5 s) is still running.

**Tests:** the scheduler's `sc_p_native_stage_memory.rs` counts the region in slots, not bytes, so it cannot show fragmentation. Failure 1 needs a byte-level test of `RingPlane` against its model in `kernel/plane/core`.
