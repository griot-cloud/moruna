# 5.2b: relibc on Moruna, one runtime with std

- **System design:** `architecture/moruna-os-system.md`, sections 5A0 and 5B.
- **Needs:** 5.0 and 5.2. **Rules:** `architecture/work/_rules.md`.

## Build

1. **Vendor relibc** at a pinned commit under `kernel/vendor/relibc`, with its licence, the commit
   and file hashes, as OSTD and OpenVMM are. Vendor only the crates the Moruna build needs (none of
   Redox's own), each with its licence; `cargo deny` passes.
2. **Moruna's platform:** a `Sys` implementing relibc's `Pal` (and the other traits as `ENOSYS`) over
   `moruna-sys`, mapped as the 5.2b assessment lists: memory, threads, futexes, time from the clock
   page, `RANDOM_READ`, exit, fd 0 to 2. Linux's ABI constants for the `target_os` sites.
3. **One runtime (5B):** one crate graph with std and the SDK; relibc's `malloc` is std's allocator;
   ELF TLS with one control block; `pthread_create` and `std::thread::spawn` on one thread path; one
   `_start`. The TLS and `_start` changes in std are 5.0's agent's; this item uses them.
4. **The C SDK on it:** `libmoruna_function.a` and the headers for the user target; `double.c` and
   the aggregate test build as static native functions.

## Success

- relibc's own C tests that need only what Moruna supports pass as booted tasks.
- 5.2's C example passes the row check in a booted job.
- A C function using `malloc`, `printf` to stderr, `pthread_create` and a `thread_local` runs.

The commits, the booted results, and which relibc tests were left out and why.
