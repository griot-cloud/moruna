# 6.3y: the object stores' requests in flight follow the room, not the worker count or the part size

- **System design:** `architecture/moruna-os-system.md`, section 3A (the arena bounds how far
  reading runs ahead, never how many workers decode) and item 3.5b (what a budget lets the object
  stores have in flight). **Rules:** `architecture/work/_rules.md`.
- **Found by:** run 6 (benchmark log, run 202611190418).

## The defect

One request to Blob from the node runs at 15 to 30 MB/s reading and about 10 MB/s writing. A run
is as fast as the requests it keeps in flight, and three rules keep that number small:

1. **Reads follow the workers.** The controller's read-ahead starts at
   `min(room / split, max(workers, READ_AHEAD_INITIAL))` (`moruna-controller` `model.rs`
   `read_ahead`), so 4 on a 4-CPU node. It rises by one a tick only while the workers idle and Q0
   is under its low water (`classify.rs`).
   - Run 6: about 2.4 reads in flight on average.
   - Q0 peaked at 87 MB of a 3.16 GB tier, and the job's whole input (843 MB) would fit in its
     7.4 GB arena.
   - The drive already bounds reads by the arena: each read is charged twice its decoded estimate,
     so reads in flight never hold more than half the arena (`source_drive.rs`). Decodes run on
     the workers. The worker cap bounds nothing the arena does not.
2. **Room buys bigger parts, not more of them.** `ObjectIo::for_room`
   (`moruna-reactor/src/object.rs`) caps the requests at the sockets (64) and then grows the part
   with the room: `part_bytes = room / requests`, 58 MB on the node.
   - An Enrich file of about 48 MB is then one put on one connection.
   - Run 6, Enrich: 25 files in 46 parts, about 2.9 writes in flight, 5.5 to 6.3 MB/s each. The
     sink's put waits on each rolled file's upload, which was 46 s of its 63 s in run 5 (6.3u).
3. **Nothing bounds requests across objects.** The reactor's `objects` semaphore takes one permit
   per operation, and a write then runs its parts in flight inside that permit
   (`object::write`). So a rule that gave a file more parts would open more connections than
   the job's sockets.

## Decided (PM, 2026-11-19)

1. **One request budget.**
   - The reactor holds one semaphore of N = `ObjectIo::requests` permits. Every request to a store
     takes one for as long as it is on the wire: each ranged read (6.3t's requests of at most
     `OBJECT_REQUEST_MAX`), each part of a multipart upload, each single put.
   - Meta operations (head, list, delete, complete, abort) take one each.
   - The per-operation `objects` semaphore goes: the request budget replaces it.
   - N is unchanged: the room over S3's least part, at least 1, at most the job's sockets.
2. **Parts at the store's least size.**
   - `part_bytes` is S3's least part (5 MiB), raised only to fit an object in S3's most parts, and
     never larger than the object.
   - An object's parts in flight are all its parts, each taking a permit of the budget. The room
     buys parallel parts, up to N.
   - The note "object stores: N requests at once in parts of …" stays, with the new figures.
3. **Reads follow the room.**
   - The controller's read-ahead is the arena's read room over a split's charge, clamped to
     `[1, READ_AHEAD_MAX]`, with no worker term. The request budget bounds what is on the wire.
     A file source keeps its own `file_depth`.
   - Its rules to lower it under a slow sink (the Sink row's back-pressure) and to raise it stay.
   - The drive's own bounds stay as they are: `arena_admits`, the evicted re-reads, an ordered
     sink's stall, and Q0's high water.
   - Decodes stay on the workers: only fetches go ahead.

## Refused

- A fixed read-ahead.
- A part size tuned to one store or benchmark.
- A request budget that is not the sockets and the room.
- Raising the sockets.

## Done when

- **Host tests:**
  - every request takes a permit, and no more than N are on the wire across reads and writes;
  - a 48 MiB object goes up in 10 parts in flight at once when N allows;
  - the read-ahead on a 4-worker run with room for 64 reads is 64 (or N), not 4;
  - the existing reactor, scheduler, controller and runtime tests pass, with tests that asserted
    the old rules rewritten to the new ones.
- **Coverage** of the lines added is at least 80%.
- **The node run** (PM): Enrich's writes, and Occupancy's and Audit's reads, in flight and in MB/s
  from 6.3u's note, against run 7.

## Built (PM, 2026-11-19)

On `feature/arrow-core-0.7`:
- **Reactor.** The object layer holds the request budget. The operations' queues take its permits,
  and `object::write` takes one per part. `for_room`'s part is S3's least.
- **Controller.** `read_ahead(queue_half, split)` is clamped to `READ_AHEAD_MAX`, with no worker
  term.
- **Tests.**
  - New: `a_writes_parts_and_the_reads_share_one_request_budget` (a 48 MiB write beside 20 reads,
    N = 6: at most 6 on the wire, 10 parts) and `a_files_parts_go_out_at_once_when_the_budget_allows`
    (10 parts on the wire at once). Both fail under the old rules.
  - Also new: `the_read_ahead_follows_the_room_not_the_workers`.
  - Results: reactor 86, controller all, runtime and scheduler 624 pass. Clippy is clean.
- **Left.** The node run against run 7.
