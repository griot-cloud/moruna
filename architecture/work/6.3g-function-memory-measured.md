# 6.3g: the room a function gets is a default, not its measured memory

- **System design:** `architecture/moruna-os-system.md`, section 3A ("A function's memory is
  measured, never assumed", amended 2026-11-18) and 3E. **Rules:** `architecture/work/_rules.md`,
  and 6.3's steps: map and measure, write the defect as a test, then **stop and report** with the
  build you propose. The PM approves before anything is built.
- **Raised by:** Brackly, 2026-11-18. Moruna's promise is that a function's memory is known from its
  warm-up on small batches, under the Arrow-in, Arrow-out contract, and extrapolated. A slice handed
  out by any other rule departs from that.

## The gap, as far as the PM has read

- **Warm-up exists, on the client only.** `crates/moruna-runtime/src/check/warmup/` runs a function
  on generated batches at several sizes and fits wall time and peak memory (`peak_per_byte`,
  retained, start-up). It runs when a function is checked (`moruna check`), on the machine that
  checks it.
- **Registration carries none of it.** `POST /v1/functions` takes a name, an address, a SHA-256
  and a signature (3E). Nothing is fetched or measured at registration.
- **The node sizes from a default:**
  - `crates/moruna-runtime/src/run.rs`: `arena_host_bytes` uses the stages' declared
    `expected_amplification`, or `DEFAULT_OUT_OF_ARENA_AMPLIFICATION = 4.0`.
  - An image task's `hints()` are the defaults.
  - `native_account::child_share` splits what the arena leaves evenly between the instances, with
    a fixed least (`NATIVE_CHILD_MIN`).
- **A lead from 3.8 and 6.2:** with nothing declared, the arena gets 2 / (2 + 4) = a third of the
  allowance, whatever the function really uses.

## Do

1. **Map it** in the code and say what is true:
   - what warm-up measures, and where its results are stored (`cost`, `cost_store`,
     `ObservationStore`);
   - what a run on the node observes per function instance (its account's peak, bytes in and out);
   - every place a default or a fixed least sizes a function's memory.
2. **Measure the gap** on the four gate functions (Score, Occupancy, Enrich, Audit): each one's
   real memory per instance per input byte, from a warm-up run and from the node reports in
   `bench-run3/bench/node/results/202611181311/node/*.job.json`, against what the node's sizing
   assumed. Give a table.
3. **Write the defect as a test:** a function whose measured need is far below, and one far above,
   the default gets a room sized by its measurement.
4. **Stop and report** with a build proposal covering:
   - how the warm-up's memory facts travel with a registration (`moruna.register`, 5.4) and what
     the node stores per image;
   - how the node refines them from each run, and where it keeps them (the function cache's
     lifetime, or longer);
   - how a function with no measurement is warmed up on the job's first small batches before the
     run is sized, and what that costs;
   - how the arena's share and the instance count (6.3e) follow from the measurement;
   - what a wrong or hostile measurement can do, given that accounts still enforce the budget.

## Refused

A better default factor; a per-benchmark declaration.

## Report

The map, the table, the test, and the proposal.
