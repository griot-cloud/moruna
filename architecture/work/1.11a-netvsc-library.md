# 1.11a: `moruna-netvsc`, the library

- **System design:** `architecture/moruna-os-system.md`, section 1F.
- **Findings to read:** `architecture/work/1.7-azure-findings.md`, sections 3 and 5.
- **Needs:** 1.9a merged (the vendored crates). Host only. **Rules:** `architecture/work/_rules.md`.

## Goal

Azure's synthetic network card, netvsc, as a library a driver process will wrap: Ethernet frames in
and out over a VMBus channel.

## Build

1. **The crate:** `kernel/drivers/netvsc/core`, package `moruna-netvsc`, `#![no_std]` with `alloc`,
   no unsafe code. It uses the vendored `netvsp_protocol` (NVSP and RNDIS) and `vmbus_ring`.
2. **The channel:** generic over `moruna-vmbus`'s `Channel` trait. If that crate (item 1.9b) isn't
   merged when you start, define the trait in your crate's `channel` module exactly as section 1F
   states it, marked `// moruna: moves to moruna-vmbus (1.9b)`. The PM reconciles at merge.
3. **Initialisation,** in netvsc's order:
   - NVSP: init with a version range (offer the newest `netvsp_protocol` defines, step down, and
     refuse anything below NVSP 5); send the NDIS version; give the host the receive buffer and
     the send buffer as GPADLs (through `Channel`), and take the section sizes it answers;
   - RNDIS: initialize; query the MAC address and the MTU; set the packet filter to directed,
     multicast and broadcast.

   There is no guest netvsc on OpenVMM's main branch. Use `netvsp_protocol`'s types, OpenVMM's
   `netvsp` (the host side) for what the host expects, and Microsoft's published RNDIS and NVSP
   documentation. Say in a comment which source each step follows.
4. **Sending a frame:** an RNDIS packet message in a send-buffer section when it fits, or by guest
   page numbers when it doesn't; the completion frees the section.
5. **Receiving:** frames arrive as RNDIS packet messages in receive-buffer sections named by a
   transfer-page packet; each is handed to the caller, then the completion gives the section back.
6. **What is refused or ignored, by design (1F):**
   - the virtual function: a `SendVfAssociation` is acknowledged and ignored, and the library never
     sends `SwitchDataPath`;
   - sub-channels, checksum and segmentation offloads, VLAN: not offered and not used;
   - link status changes are reported to the caller.
7. **What `moruna.driver.net` needs** (`kernel/drivers/net-protocol`): MAC, MTU, link state, send a
   frame, receive a frame. Nothing more.
8. **A fake netvsp,** in the tests: the host's side over an in-memory `Channel`, strict about order
   and sizes, able to offer a virtual function and to inject frames.

## Success

Host tests: initialisation including a version step-down and a refusal below NVSP 5; MAC and MTU
read; 1,000 frames each way with their bytes intact, sizes from 60 to the MTU; the send buffer
running out and recovering; a VF offer ignored with traffic continuing; a link-down then link-up
reported; garbage from the host refused without a panic; a fuzz-style run of 10,000 random host
packets with a fixed seed. 80% line coverage. Builds for the user target.

## Not yours

The driver process, the `vmbus` process, MANA, anything booted.
