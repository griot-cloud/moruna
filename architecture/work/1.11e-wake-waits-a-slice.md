# 1.11e: A woken thread waits behind a busy one for up to a slice

- **System design:** `architecture/moruna-os-system.md`, section 1F (netvsc, VMBus), and the
  core's scheduler (`kernel/core/src/sched.rs`, SDD 20 f.11). **Rules:** `architecture/work/_rules.md`,
  and 6.3's steps (`architecture/work/6.3-each-miss.md`): diagnose, write the defect as a test, then
  stop and report before fixing.
- **Found by:** 1.11d (merged, 04806d26).

## The lead

`kernel/core/src/sched.rs` runs each CPU's queue first in, first out. A task keeps its CPU across
waits and wakes. A queued task takes the CPU only when the running task waits, exits or yields, or
when it has run for `SLICE_TICKS` (10 ticks of 1 ms). So a thread woken by an interrupt, on a CPU
where another thread is computing, waits up to 10 ms, even when another CPU is idle.

Every request and reply the node makes passes through such wakes: netvsc's and storvsc's
completions, the vmbus process's signals, the network server, `api`, and the engine's object reads
(3.4, 3.5). A job keeps every CPU busy with its workers, which is exactly when these threads must
run at once. 1.11d measured send completions 10–26 ms after the commit on Azure, most of it its own
console printing, with 0–5 ms left per frame. The wake path is the separate lead named here.

## Do

1. **Measure** it without Azure: on the host, if the scheduler's queue policy can be driven there,
   and in a booted QEMU node in `moruna-arm` (lock turn). Use one CPU-bound thread per CPU and one
   thread that waits on an event and is woken by an interrupt or by another thread. Report:
   - the wake-to-run latency at the median, p99 and max, with all CPUs busy and with one CPU idle;
   - the same with the network: one object read or `/v1/health` round trip under a job that fills
     every CPU.
2. **Name the cause** in the code: the slice, FIFO placement behind a running task, a woken task
   kept on a busy CPU while another is idle, the stretched tick, or something else the measurement
   shows.
3. **Write the defect in general terms** as a failing test: for example, "a thread woken while
   another thread computes on its CPU runs within N µs", with N justified by the measurement.
4. **Stop and report to the PM** with the fix you propose and the alternatives. Candidates to weigh:
   - preempting the running task when a woken one has waited (a wake preempts a task past a short
     minimum);
   - placing a woken task on an idle CPU. Note `sched.rs`'s comment on why a parking task is not
     migrated at dequeue, and say how the proposal avoids that hazard;
   - a shorter slice.

   For each, say what it costs the engine's workers (switches per second, cache) and how it stays
   the same on the host, the VM and the microkernel.

## Refused

A priority that only the network or driver threads get by name; a slice tuned to one benchmark.

## Report

The measurements, the cause, the test, and the fix proposed with its alternatives.
