# 1.2: Boot lines, deadlines and power-off

- **System design:** `architecture/moruna-os-system.md`, section 1B.
- **Needs:** 1.1. **Rules:** `architecture/work/_rules.md`.

## Goal

A node always says how far it got, and a node that fails says why and turns itself off, on every
machine, not only under QEMU's test exit device.

## Build

1. **The core's line.** After every CPU is online, the core prints exactly
   `moruna: core <version> cpus=<n> memory=<bytes>`: `<version>` is the `moruna-microkernel`
   crate's version, `<n>` the online CPUs, `<bytes>` the usable RAM in the boot memory map.
2. **Fatal lines.**
   - A fatal error in the core (a refused boot, a panic) prints `moruna: fatal core: <reason>`.
   - A service that cannot go on prints `moruna: fatal <stage>: <reason>` and exits with failure.
   - When any service ends, the supervisor prints `moruna: fatal service <name>: ended`, kills every
     child, and exits with failure. The core then powers off, as it already does when every process
     has ended (`kernel/core/src/process.rs`).
3. **Power-off, in this order:** QEMU's test exit device (a harmless write where it is absent), then
   ACPI S5 as 1B says, then a halt loop. This is a marked patch in the vendored OSTD
   (`src/arch/x86/power.rs`), with a `moruna:` comment as earlier patches have; you have approval
   for that patch.
4. **Deadlines on boot waits.** OSTD's PIT calibration (`src/arch/x86/kernel/tsc.rs`) and APIC timer
   calibration (`src/arch/x86/timer/apic.rs`) wait without end. Give each a deadline of 2 s of
   wall time, counted on the TSC without its rate (as a raw count above 2^33, about 2 s at any rate
   a cloud CPU runs). On expiry: `moruna: fatal core: <which> calibration timed out`, then power-off.
   Same marked-patch rule.
5. **The services deadline.** The supervisor prints `services started` only when every service in
   `node.conf` has started, within 5 s of its own start. Otherwise it prints
   `moruna: fatal services: <name> did not start within 5 s`, and stops as in step 2.

## Success

- On `uefi-boot.sh` (1.1) at 1 and 2 CPUs: the core's line, then `services started`, with the right
  CPU count.
- **S5 proven:** with a node.conf naming a program the image lacks, the boot prints the
  supervisor's fatal line, and QEMU exits by itself within 10 s. QEMU has no test exit device in
  this machine, so only S5 can end it.
- **Calibration deadline proven,** if QEMU's `-machine q35,pit=off` is available under the
  emulator: the calibration fatal line, then a power-off. If it is not, say so, and prove the
  deadline in a host test of the patched function's logic.
- The supervisor's 5 s deadline is proven in a host test.
- CI's boot (`kernel/tools/boot.sh` and `check-boot.sh`) still passes on 1, 2 and 4 CPUs, with its
  exit codes unchanged.

## Not yours

Network, `platform`, `api`, and any other boot line. Any change to the core beyond the line, the
fatal line, power-off and the two deadlines.

## Report

The commits, the boot logs of each success check, and the patch lines in the vendored OSTD.
