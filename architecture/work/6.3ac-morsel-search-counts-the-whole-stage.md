# 6.3ac: the morsel-size search counts the function's CPU per byte and none of the engine's

- **System design:** `architecture/moruna-os-system.md`, section 3A (the engine sizes from what a
  run observes), and SDD 11 f.4b (the throughput search). **Rules:** `architecture/work/_rules.md`.
- **Found by:** run 9 (benchmark log). Every job was about 5% slower than run 8b. The search
  settled on smaller morsels:
  - Score went 16.8 → 8.4 → 4.2 MB, against 15.9 → 8.0 → 5.7 MB;
  - Audit settled at 8.4 MB, against 16.8 MB.

  So Score read in 863 pieces against 465, and decoded for 34.9 s against 25.7 s, summed over
  the workers.

## The defect

The rule sizer's search (`crates/moruna-controller/src/sizer/rule.rs`) halves the target while a
morsel's cost per byte (`cost_at`, from the records' `cpu_time_us`) falls by `SEARCH_GAIN`.

- **Since 6.3m and 6.3z,** a ring stage's record carries its morsel's function time, the task's
  pieces. That is the right figure for the function, but it is the only cost the search sees.
- **A smaller morsel is cheaper for the function** (it stays in the cache), so the search halves.
- **It costs the engine more:**
  - more reads, each with a fixed decode cost (6.3l);
  - more pieces posted and taken;
  - more batches encoded.

  None of that is in `cost_at`. Before 6.3z the record carried the engine worker's CPU for the
  unit, which leaned the other way.

## Decided (PM, 2026-11-19)

1. **The search's cost at a size is the stage's whole CPU per byte at that size:**
   - the function's: the records' times, as now;
   - plus the engine's for the same bytes: the worker's own CPU for the units, and the source's
     decode and the sink's encode over the window the size ran, from their cumulative counters
     (the deltas over that window, per input byte).
2. **The records keep the function's time.** The engine's share is measured per window, not
   estimated, and joins it in `cost_at`, so the search sees both.
3. **A stage with no ring task is unchanged** in what it measures. Its records already carry the
   unit's CPU. Adding decode and encode applies to it as well, so it gets the same rule.
4. **The note says what the search settled on and why:** "stage N settled at B bytes a morsel,
   where the stage spent the least CPU per byte (the function's F ns, the engine's E ns a byte)".

## Refused

- A floor on the morsel size.
- Turning the search off.
- A weight or constant on either side of the sum.
- Measuring wall time in place of CPU.

## Done when

- **A host test fails first:** a stage whose function's CPU per byte falls with smaller morsels
  while the engine's per-morsel cost rises. Today it settles small; with the fix it settles where
  the sum is least.
- **The existing sizer and controller tests pass.**
- **Coverage** of the added lines is at least 80%.
- **The node run (the PM):** run 10 against runs 8b and 9.

### Corrected at the helper's stop (PM, 2026-11-19)

The premise above was wrong.
- **What the record carries.** A trace record's `cpu_time_us` is still the engine worker's CPU for
  the unit (`worker.rs` `record_of`/`build_record`); 6.3z's `Given` time reaches only the cost
  model.
- **What 6.3m's bookkeeping does instead:**
  - a unit that completes no morsel leaves no record, so its CPU is lost;
  - a unit that completes several puts its whole CPU on each.

  Either may be what moved the search in run 9.

**The decision replaces Decided 1 to 3:**
- **The search's cost** comes from cumulative per-stage counters, as window deltas:
  - the worker CPU over all the stage's units;
  - the task CPU (the ring morsels' `Given` cpu);
  - decode CPU charged to the stages a source feeds directly;
  - encode CPU charged to the stages that feed a sink directly;
  - divided by the stage's input bytes.
- **CPU, not wall:** decode and encode are measured as thread CPU, as the worker's unit CPU is.
- **Records:** a unit's CPU is split evenly among the morsels it completes, and a unit with none
  adds to the counter only (SDD 30 d.4).
