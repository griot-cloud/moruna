# 2.2b: The API in the node

- **System design:** `architecture/moruna-os-system.md`, sections 1D, 2B and 2C.
- **Needs:** 1.4 and 2.3 merged; 2.4 merged for the MCP check. **Rules:** `architecture/work/_rules.md`.

## Goal

The node's `api` program serves the real API, through `moruna-api-server`, on 443.

## Build

1. **Wiring** in `kernel/node/api` (`moruna-node-api`): the network server's sockets become the
   library's transport; each accepted connection is one server connection. Single-threaded, polling
   the sockets and the `platform` link.
2. **From the hand-over (1.4):** token keys and instance ID for 2C; `tls` for the operator's identity,
   or `Identity::generate` when it is absent; the wall clock, carried forward as the hand-over's
   wall clock plus the core's monotonic time since it was read.
3. **The node document:**
   - `version`: the `moruna-node-api` crate's version;
   - `cores`: `moruna_sys::start::cpus()`;
   - `executors`: `[{"kind":"cpu","slots":cores}]`;
   - `memory_bytes`, `instance`, `cloud` and `boot_ms`: from the hand-over, which gains
     `memory_bytes` and `boot_ms` from `platform`. `platform` reads memory from the core's boot
     information. If no call gives it, ask.
   - `time`: the wall clock now; `health`: `"ok"`.
4. **The console line** `moruna: tls sha256=<fingerprint>`, printed before `api` answers `ready`.

## Success

Booted with `uefi-boot.sh` against the fake OpenStack of 1.4, with `hostfwd=tcp::8443-:443`, and
a node config whose `token_keys` holds a test key:
- `curl -k https://localhost:8443/v1/health` answers `{"status":"ok"}`;
- `node` with an `observe` token answers the node document, with the right CPU count and instance ID;
- `node/audit` with an `admin` token shows those calls;
- a bad token gets `unauthorized`;
- `moruna node --pin <the console fingerprint>` (2.5's CLI) reads `node`;
- MCP `tools/call` of `moruna_node` answers, once 2.4 is merged;
- 1 and 2 CPUs.
