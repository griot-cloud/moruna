# 6.3i: the node does not report a job's CPU

- **System design:** `architecture/moruna-os-system.md`, sections 3A, 3B (the report) and 6B (what
  the benchmark measures: CPU seconds beside operational time). **Rules:** `architecture/work/_rules.md`.
- **Found by:** 6.2 run 3 and item 6.2c. Every node report has `resources.cpu_core_s: 0.0` with
  `usage_measured: false`, and its notes say CPU is not measured. The function task's own
  `cpu_core_s` is not the job's either: 2.8 s for Score against 81.8 s busy.

## Why it matters

The benchmark's bar has a CPU half: Moruna's CPU seconds against the least of any engine. A node
that cannot say what a job cost cannot be compared, and an operator cannot bill or size from it.

## What exists

The core counts each process's CPU (`cpu_ns` in `kernel/core/src/process.rs`, answered through
`clock_gettime`'s process CPU clock).

## Do

1. **Map** what CPU a job uses on the node: the engine process and its workers, each function
   instance, and the services that work for it (the network server, drivers, imagefs, `api`). Say
   which the job's account can be charged with, and how the core exposes each.
2. **Write the defect as a test:** a job that computes for a known time reports
   `resources.cpu_core_s` within a tolerance of it, with `usage_measured: true`.
3. **Build it:**
   - the report's `cpu_core_s` is the CPU of the job's own processes (the engine and its function
     instances), read from the core's counters at the job's end;
   - the services' CPU on the job's behalf is given as a separate figure if the core can attribute
     it, or stated as not attributed;
   - each function task's `cpu_core_s` is its instances' CPU.

   Ask the PM before adding a core call or changing the report's schema beyond these fields.
4. **Booted check:** a job on a 4-CPU node reports CPU that agrees with its workers' busy time
   within a stated tolerance.

## Report

The map, the test, the build, the booted lines, coverage and the commits.
