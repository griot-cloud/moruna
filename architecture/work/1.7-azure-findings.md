## Summary

1. **What stops today's core on Azure** [inf]: three things, none with a `fatal` line. Unless
   Hyper-V's CPUID gives a crystal frequency (leaf 0x15) and TSC-deadline mode, which 1.7b must
   check, the TSC and APIC-timer calibration fall back to the PIT, which Generation 2 does not have,
   and the boot processor halts waiting for a PIT interrupt. Past that, the manifest's `root.ecam`
   needs an ACPI MCFG, which a machine with no PCI bus does not have, so the core refuses the boot.
   And OSTD can power off only under QEMU, so every refusal ends in a halt that Azure shows as
   running.
2. **What Hyper-V gives in their place** [doc]: the TSC and APIC-timer frequencies in two MSRs, a
   10 MHz reference counter, a virtual local APIC timer, and the SynIC (hypercall page, message and
   event pages, an interrupt vector of the guest's choosing) on which VMBus runs.
3. **What OpenVMM saves us** [src, inf]: the definitions, under MIT and no_std: Hyper-V's constants
   (`hvdef`), VMBus's messages (`vmbus_core`), the ring buffer (`vmbus_ring`), NVSP and RNDIS
   (`netvsp_protocol`), and storvsc's types after a few-line fork. It has no guest client we can run:
   its VMBus client, storvsc and MANA drivers are std and async, and it has no guest netvsc. Using
   any of it means vendoring, since it is not on crates.io and `deny.toml` refuses git sources.
4. **Two Azure facts for 1F** [doc]: `Standard_D4ls_v5` lists accelerated networking as
   *Required*, so 1F's "accelerated networking off" cannot be set (netvsc alone still carries
   traffic); and Azure's CLI and portal create Generation 2 machines with Trusted Launch and Secure
   Boot unless told `Standard`, which an unsigned GRUB cannot pass. Section 5 lists these and four
   more for the PM.

**ACPI tables read** [src]: the RSDP comes from GRUB's multiboot2 tag (`x86/boot/multiboot2/mod.rs:87-99`;
on an EFI boot with no tag, ACPI is absent and `x86/irq/chip/mod.rs:170` panics). Then the MADT
(`x86/irq/chip/mod.rs:171`, and the CPU count at `x86/boot/smp.rs:54-107`), the FADT
(`x86/kernel/acpi/mod.rs:146-156`: century, boot flags, reset register), the MCFG (`:158-168`), the
DMAR (`x86/kernel/acpi/dmar.rs:79`, for the IOMMU; its absence is a warning, `x86/mod.rs:111-114`)
and the HPET table (dead code). The DSDT is not read. Microsoft does not document which tables a
Generation 2 machine carries: **unknown until 1.7b** beyond the inferences above.

**Port 0x61** (NMI status), which "Generation 2 instances don't support" (`linux:
arch/x86/kernel/cpu/mshyperv.c:705-706`), is not touched by OSTD or the core [src: no match].

**What stops the core, in order** [inf until 1.7b]:

1. `x86/kernel/tsc.rs:22-24`: if leaf 0x15 has no crystal frequency, the PIT fallback hangs.
2. `x86/timer/apic.rs:22-25`: if TSC-deadline is absent, the PIT fallback hangs.
3. `x86/irq/chip/mod.rs:265-270` and `ostd/boot/smp.rs:197-205`: unlikely stops.
4. `core/clock.rs:76`: the CMOS read; expected to work.
5. `core/boot.rs:111`: certain with today's manifest: no MCFG, so no `root.ecam`.
6. After that, `devices` has no PCI to walk: no disk and no network.

None of these prints a `fatal` line, and none powers the machine off.

## 2. What the core needs from Hyper-V

Rows 1 to 3 are what `services started` needs. Rows 4 to 7 are the VMBus mechanism of 1F (item 1.9).
TLFS is Microsoft's Hypervisor Top Level Functional Specification.

| # | Piece | What the guest does | Defined in |
|---|---|---|---|
| 1 | **Finding the hypervisor** | CPUID.1:ECX[31] set; leaf 0x40000000 returns the highest leaf (at least 0x40000005) and `Microsoft Hv`; leaf 0x40000001 returns `Hv#1`. Microsoft asks guests to decide by the interface signature `Hv#1`, not the vendor name. | [TLFS, Feature and Interface Discovery](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/tlfs/feature-discovery): "Hypervisor Discovery", "Microsoft Hypervisor CPUID Leaves" [doc] |

| 4 | **The hypercall page** | Write a non-zero guest identity to MSR 0x40000000 (`HV_X64_MSR_GUEST_OS_ID`); then write a page number with the enable bit to MSR 0x40000001 (`HV_X64_MSR_HYPERCALL`); map that page executable; call its first byte with the input value in RCX, the input and output GPAs in RDX and R8, the result in RAX. | 6 | **The message and event pages** | Per virtual processor: SCONTROL (MSR 0x40000080) enables the SynIC; SIEFP (0x40000082) and SIMP (0x40000083) place the event-flags page and the message page; SINTx (0x40000090 + x) sets each source's vector (16 to 255), mask, auto-EOI and polling; EOM (0x40000084) asks for the next queued message. The ACPI device `VMBUS` or `VMBus` carries MMIO ranges for devices that need MMIO (the virtual PCI bus, the frame buffer); storvsc and netvsc use rings in guest memory and need none [inf]. | Delivery: [TLFS, Inter-Partition Communication](https://learn.microsoft.com/en-us/virtualization/hyper-v-on-windows/tlfs/inter-partition-communication) [doc]. **What VMBus itself is defined by**: not the TLFS. The TLFS defines the SynIC and the hypercalls.
Offers, GPADLs, channel opening and the ring layout are defined publicly only by implementations:
Linux's `drivers/hv` (GPL-2.0) and OpenVMM (section 3) [inf from the pages above].

**What follows for 1F's VMBus split** [inf]:

- The core's mechanism needs more than the two hypercalls: the SynIC MSRs (SCONTROL, SIMP, SIEFP,
  SINT2, EOM) are written at CPL 0, so the EOM write after a pending message is a kernel operation
  too.
- The SynIC is per processor. Either the core gives the `vmbus` process one message page and one
  event page per CPU, or every channel is opened targeting one CPU. The choice is the PM's.
- A GPADL names guest physical page numbers, so the `vmbus` process and its drivers need the
  physical addresses of the memory they share with the host.

**What OpenVMM saves us** [inf]:

- The definitions: every Hyper-V constant and layout (`hvdef`, `x86defs`), every VMBus message
  (`vmbus_core`), the NVSP and RNDIS types (`netvsp_protocol`), and, after a few lines of fork, the
  storvsc types. These are the parts with no public specification.
- The ring buffer (`vmbus_ring`), no_std and free of unsafe code.
- References, under MIT, for everything stateful: the VMBus client, storvsc, MANA, and the hypercall
  page. They show the order of operations, but they run on OpenVMM's async runtime and are not usable
  in a Moruna process.
- A Hyper-V-like host for testing on Linux with KVM (section 5).

**What it does not save us** [inf]: the VMBus client state machine, storvsc's and netvsc's drivers,
and anything in the core.

## 5. Other findings for the PM

These are facts that bear on 1F's decisions. The decisions are the PM's.

- **Accelerated networking cannot be off on `Standard_D4ls_v5`.** The Dlsv5 page lists it as
  "Required", with interfaces "NetVSC, ConnectX, MANA" ([Dlsv5 series](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/general-purpose/dlsv5-series))
  [doc]. "Disabling Accelerated Networking on VM sizes where Accelerated Networking is listed as
  'required' does not have any effect", and the VF is offered regardless. But "If a VM image doesn't
  include a driver for the host's physical NIC, networking continues to work through the virtual
  NIC": on ConnectX hosts at "the slower speeds of the virtual NIC", on MANA hosts at
  "near-line-rate" ([Accelerated Networking](https://learn.microsoft.com/en-us/azure/virtual-network/accelerated-networking-how-it-works))
  [doc]. So netvsc alone works; the node must ignore the virtual-PCI offer and never ask to switch
  the data path to the VF [inf].
- **Trusted Launch is Azure's default.** "Creating VMs defaults to Trusted Launch for Azure portal,
  CLI, or PowerShell", and with Secure Boot "all OS boot components (boot loader, kernel, kernel
  drivers) require trusted publishers signing" ([Trusted Launch](https://learn.microsoft.com/en-us/azure/virtual-machines/trusted-launch))
  [doc]. 1A's unsigned GRUB would not boot. The bring-up recipe needs security type `Standard`
  (API version 2025-11-01 or later, same page) [doc].
- **The "ready" report needs a second outbound grant.** It is an HTTP GET of
  `http://168.63.129.16/machine?comp=goalstate` and a POST of a `Health` XML document to
  `/machine?comp=health`, both with `x-ms-version: 2012-11-30`, after DHCP; "Failing to report ready
  to Azure will result in your VM being rebooted!" ([Linux images without a provisioning agent](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/no-agent))
  [doc]. 1C grants `platform` only the instance-data address, so this needs 168.63.129.16 port 80
  as well [inf].
- **"The first that answers names the cloud" needs a status.** Azure's instance data answers
  `400 Bad Request` when the `Metadata: true` header is missing and `404 Not Found` for an unknown
  path ([Instance Metadata Service](https://learn.microsoft.com/en-us/azure/virtual-machines/instance-metadata-service),
  "Errors and debugging") [doc]. An OpenStack-first probe on Azure gets an answer [inf]. The same
  page says `userData` is "Base64 encoded", that requests are limited to 5 per second, and that a
  `410 Gone` is retried "for a max of 70 seconds" [doc].
- **Power-off on a fatal error** needs ACPI S5 on Azure, which needs the DSDT's `\_S5` (section 1,
  isa-debug-exit row) [inf].
- **A Hyper-V host without Azure.** OpenVMM runs on Linux with KVM, boots guests with UEFI
  (`mu_msvm`), and has the VMBus devices storvsp and netvsp ([OpenVMM guide](https://openvmm.dev/guide/index.html))
  [doc]. A Linux machine with KVM could then exercise items 1.8 to 1.11 without uploading a VHD per
  try; Dlsv5 supports nested virtualization ([Dlsv5 series](https://learn.microsoft.com/en-us/azure/virtual-machines/sizes/general-purpose/dlsv5-series))
  [doc]. It is not Azure's host, so Azure remains the proof [inf].

## 6. 1.7b: the image booted on Azure (PM, 2026-11-17)

**Setup.**
- Image: `moruna-node.vhd` of item 1.5 (commit `b7613cc9`, 71,303,680 bytes, SHA-256 `93e44f73…`).
- Machine: one `Standard_D2s_v4` in `griot-dev`, Central India, zone 3. Generation 2 from a
  specialized managed disk, security type `Standard`, accelerated networking off, no public
  address.
- Boot diagnostics were enabled before a restart, so the serial log covers the whole boot.
- Both resource groups were deleted afterwards. The script is in the PM's scratchpad,
  `pm-1.7b/boot-azure.sh`.

**What it showed: firmware, GRUB and OSTD's start-up all work on Hyper-V.**
- GRUB loaded the core by multiboot2 from the GPT disk. It warned "no console will be available
  to OS" and "no suitable video mode found": the multiboot2 header asks for a video mode Hyper-V's
  firmware doesn't offer. The serial console still works.
- OSTD read the memory map: 11 GiB of address space, about 8 GiB usable, as the size has.
- It read the MADT (two local APICs), built the kernel page table, and found the xAPIC and the
  I/O APIC.
- **The last line** is `INFO: irq: IOAPIC override: ISA interrupt 9 for GSI 9`. Nothing follows,
  and the machine stays "running".

**What that confirms** [inf]: the next step in OSTD's boot is the TSC calibration against the PIT,
which a Generation 2 machine doesn't have (1.7a, section 1). That is the wait 1.2 gives a deadline
and 1.8 avoids by reading Hyper-V's frequency MSRs. It also confirms that firmware, GRUB, the
memory map, ACPI's MADT and the interrupt controllers need nothing new. The next Azure boot is
with 1.2 and 1.8 merged.

**One thing to fix:** the multiboot2 header's video-mode request. A node has no screen, so the
header should ask for none (text mode). That belongs to 1.2, `kernel/boot`.
