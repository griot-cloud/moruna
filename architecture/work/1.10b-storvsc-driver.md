# 1.10b: The `storvsc` driver process

- **System design:** `architecture/moruna-os-system.md`, section 1F.
- **Needs:** 1.9c and 1.10a merged. **Rules:** `architecture/work/_rules.md`.

## Build

`kernel/drivers/storvsc/server`: a driver process that opens each SCSI controller channel through
`vmbus`, and serves `moruna.driver.block` for each disk it finds, using `moruna-storvsc`. Data moves
by the guest page numbers of the client's memory, with no copy. It is started by the supervisor
when `vmbus` runs.

## Success

- On Azure (as 1.9c), the node reads its OS disk's GPT header through the block protocol, and reads
  and writes an attached data disk.
- The block driver conformance suite (`kernel/drivers/block-test`) passes against it on Azure.

## Cloud

You create nothing. Finish the host part (host tests against `moruna-vmbus`'s fake host, at the 80%
floor), save the cloud image (VHD) from your lock turn, and report. The PM runs the Azure boot and
sends you the serial log to judge.

## DMA

Your process gets its own whole copy of `root.dma` (1F's Hyper-V DMA rule). Pin a client's memory
as `kernel/drivers/virtio-blk` does; long-lived buffers go through `vmbus`'s `share`.

## Report

The commits, the host tests, and the saved image's path.
