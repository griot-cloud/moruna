# 2.3: Tokens and the audit record

- **System design:** `architecture/moruna-os-system.md`, section 2C.
- **Needs:** 2.2. **Rules:** `architecture/work/_rules.md`.

## Goal

Every call but `health` needs a valid token with the right scope, and every call leaves an audit
record that `node/audit` returns.

## Build

1. **Verification,** in `moruna-api-server`: `Authorization: Bearer <JWT>`, compact form, header
   `{"alg":"EdDSA","typ":"JWT"}` (`typ` optional), Ed25519 through `ring`. The claims are 2.1's
   `Claims`. A call is allowed exactly when 2C's four conditions hold. The keys and the instance ID
   come from the caller, from node config.
2. **Answers:** a missing, malformed or unverifiable token, a wrong `aud`, or an `exp` in the past
   or more than one hour ahead: `unauthorized`. A valid token without the scope: `forbidden`.
   `health` never reads the header.
3. **Audit:** one record per call, as 2.1's `AuditRecord`, in a ring of the last 10,000 records,
   newest first in `node/audit`. `key` is 2.1's key ID of the key that verified the token, or empty.
   Nothing is written anywhere else.
4. **A test helper,** in the crate's tests only: makes a key pair and signs claims, for every later
   test.

## Success

Host tests, each over the TLS transport of 2.2:
- each of these is refused with its answer: a bad signature, a token signed by a key not in the
  list, a wrong `aud`, an expired `exp`, an `exp` more than an hour ahead, an `alg` other than
  `EdDSA`, a malformed token, a missing header;
- `observe` reads `node`, `observe` is forbidden `node/audit`, `admin` reads both;
- after N calls, `node/audit` shows them newest first, with the right key ID, operation and status;
  after 10,001 calls it holds exactly 10,000.
- 80% line coverage of what you add.
