# 6.3o: the cost model and the adaptive policies are dormant on the node

- **Design:** `architecture/adaptive-runtime.md` (the cost model, warm-up, the observation store,
  the scheduling-policy port, decided 2026-10-28) and `architecture/moruna-os-system.md` 3A and 4H.
  **Rules:** `architecture/work/_rules.md`, and 6.3's steps: map, measure, write the defect as a
  test, then **stop and report** before building.
- **Found by:** the PM, reading 6.2 run 3's node reports (2026-11-18), and 6.3g's map.

## The miss

Every node job in run 3 reports the following:
- `policy.name: admission`;
- `policy.predicted_by_model: 0`;
- `policy.learning: null`;
- `plan.totals.basis: default`.

The node starts the engine without an observation store
(`kernel/node/protocol/src/lib.rs`, `crates/moruna-runtime/src/host/session.rs`; 6.3g's map). So
the cost model has nothing to predict from, and the residency-aware policies the adaptive runtime
built (`residency_greedy`, `lookahead`, in `crates/moruna-scheduler/src/policies/`) never run there.
Every job starts from the same seeds and learns nothing for the next one.

On the node, the adaptive runtime's four decisions (what runs next, where, with what memory, at
what batch size) are therefore made without the model the design built for them.

## Do

1. **Map it:**
   - what the node's engine is given and what it is missing: a store, warm-up results, a policy
     setting;
   - what `explain` and the scheduler would use if they had them;
   - what 6.3g already carries to the node (function memory facts through `api`'s `spec` message,
     its phases 2 and 3), so this item extends that path and does not duplicate it.
2. **Measure** on the host, with a store holding warm-up and run observations for the four gate
   functions:
   - which policy the design's rule picks ("the default is whichever wins on measurements",
     adaptive-runtime decision 4);
   - what each policy does to wall time, idle-while-ready time and unused memory on a month and a
     year at the node's budget;
   - compare with the `admission` policy the node runs today.
3. **Write the defect as a test:** a node-mode run whose store holds observations predicts with the
   model (`predicted_by_model` above 0), and records what it learned for the next run.
4. **Stop and report** with a build proposal:
   - where the node keeps observations: in `api`, beside 6.3g's facts, per function image and
     schema;
   - how they reach the engine and come back in the report;
   - which policy is the default, by measurement;
   - what is refused: no change of policy without the measurements.

## Report

The map, the measurements, the test, and the proposal.
