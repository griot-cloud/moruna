# 1.1: The cloud profile boots under UEFI

- **System design:** `architecture/moruna-os-system.md`, sections 1A and 1B.
- **Needs:** 0.1 (a tree that boots).

## Goal

The node's disk image, built for a new `cloud` profile, boots in QEMU from UEFI firmware with one
virtio disk and one virtio network card, and prints `moruna: services started`. No direct kernel
load, no vsock, no host socket.

## Build

1. **The profile.** Add `kernel/node/cloud.image`, written like `kernel/node/standalone.image`,
   with only:
   - process `node-supervisor`;
   - program `devices`;
   - data `node.conf`;
   - drivers `virtio-blk`, `virtio-net`, `nvme`, `gve`, with the IDs `standalone.image` uses.

   No `virtio-vsock`, `imagefs`, `linux`, `node-admission`, `storage` or `engine`.
2. **Its config.** `node.conf` for this profile is exactly:

   ```
   moruna-node 1
   service devices image.devices 67108864
   bootstrap devices devices
   grant devices drivers drivers
   grant devices driver.virtio-blk driver.virtio-blk
   grant devices driver.virtio-net driver.virtio-net
   grant devices driver.nvme driver.nvme
   grant devices driver.gve driver.gve
   ```

   No network server yet: it refuses a config with no listener grant, and the only listener, `api`
   on 443, arrives in 1.3 (PM, 2026-11-17). If the `virtio-net` driver can't run without a network
   server, leave its grant out too. The files are `kernel/node/cloud/node.conf`, built with
   `--assets kernel/node/cloud`.

   The names follow `kernel/node/tools/configure.py`. If one of these lines cannot be expressed
   as written, ask.
3. **The tools.** `kernel/node/tools/package.py` and the `moruna-node-image` tool take a profile,
   `standalone` (today's behaviour, unchanged) or `cloud`. For `cloud` they check only what the
   profile lists: no engine config, no agent port, no layers, no launcher descriptor.
4. **One line from the supervisor.** When every service in `node.conf` has started, it writes
   `moruna: services started` to the console. This is the only boot line of 1B in this item.
5. **The boot script.** `kernel/node/tools/uefi-boot.sh OUT CPUS` runs exactly this machine and
   exits 0 when the line appears within 120 s under KVM, or 900 s under the emulator:

   ```
   qemu-system-x86_64 -machine q35 -smp CPUS -m 2G -nodefaults -no-reboot -display none \
     -drive if=pflash,format=raw,readonly=on,file=<QEMU's edk2-x86_64-code.fd> \
     -drive if=pflash,format=raw,file=<a fresh copy of QEMU's edk2 vars file> \
     -drive if=none,id=boot,format=raw,readonly=on,file=OUT/moruna-node.raw \
     -device virtio-blk-pci,drive=boot,disable-legacy=on \
     -netdev user,id=net0 -device virtio-net-pci,netdev=net0,disable-legacy=on \
     -serial file:OUT/console.log
   ```

   Under KVM add `-accel kvm -cpu host`; otherwise `-accel tcg -cpu max`. The boot disk is
   read-only on purpose: the node never writes it.
6. **Fix what stops the boot,** within these limits:
   - Allowed: reading what the firmware and GRUB hand over (the multiboot2 tags, the ACPI tables
     found through them), the GRUB config, the tools, the profile.
   - Ask first: any change inside `kernel/core` beyond reading boot information, any change to
     the vendored OSTD, any new driver, any change to a service's protocol.

## Success

- `uefi-boot.sh` exits 0 on 1 CPU and on 2 CPUs, three times each.
- The console log shows no panic and no `fatal`.
- `package.py --profile standalone` still builds what it built before (same file list).
- Tests for the tools' new profile argument, including a refusal of an unknown profile.

## Not yours

DHCP working, any listener, the `platform` and `api` processes, the other boot lines, qcow2 or
VHD, any cloud, the Linux-node launcher, speed.

## Rules

- Your branch starts from `feature/arrow-core-0.7`. Local commits only, with the trailers
  `Signed-off-by: Moruna Agent <agents@griotdata.com>` then `Co-Authored-By`. Never push.
- Tests ship with the code: at least 80% line coverage for the code you add to Moruna's crates.
- `package.py` needs Linux tools (`grub-mkstandalone` for x86_64-efi, `sgdisk`, mtools). The
  project's Linux container on this Mac, `moruna-arm`, is arm64. If the x86_64 EFI GRUB files
  cannot be had there, say what you need. Do not build a workaround.
- Builds and boots on the Mac need `~/.vm-lock` (`tools/proof-lab/run.py`). Never steal it. Keep
  a VM at or under 6 GiB. Release it the moment you stop.
- The disk is nearly full: build with `CARGO_INCREMENTAL=0` and delete `target` when you stop.
- Where this document and the system design leave a choice open, ask the PM. Do not choose.
