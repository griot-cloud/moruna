# 3.4: The network for jobs

- **System design:** `architecture/moruna-os-system.md`, section 3D.
- **Needs:** 3.2. **Rules:** `architecture/work/_rules.md`.

## Goal

A job reaches the object stores its document names, over HTTPS, and nothing else.

## Build

1. **The connector:** `moruna-net`, an object-store connector beside `unix://` and `vsock://`
   (`moruna-hosted-engine.md` 4.6). It opens a TCP connection through the network server's client,
   asks for TLS with `start_tls` and the node's `tls.roots`, and then carries HTTP/1.1 like the
   others.
2. **Egress per job:** `node-admission` gets a network-server client with only the `grant` right.
   For each job it mints the engine's network channel, with `connect` and `resolve` limited to the
   host names in the job's object-store settings, on port 443.
3. **`tls.roots`** in the cloud profile is the Mozilla root set, the same file the standalone node
   uses. If none is in the tree, ask.
4. **The time anchor (3D):** a link from `platform` to the network server; `platform` sends the wall
   clock once it has it, and the network server accepts `start_tls` only after that.

## Success

- On a booted node with QEMU's user network: a test job reads an object from an HTTPS server on the
  host, at a name the job lists. The server's certificate comes from a test root added to
  `tls.roots` for that boot only.
- The same job, with a second URL whose host it doesn't list, fails with a refusal naming the host.
- Throughput: one 1 GiB object read through the connector on the node, MB/s, against `curl`
  reading it on the host. The run is under the emulator, so record the figure; it is not a target
  until it runs on a cloud.

## Report

The commits, the boot log, the refusal, and both throughput figures.
